# inloop継続開発ハンドオフ

現在地だけを記録します。考え方は[docs/concept.md](../docs/concept.md)、構成は[docs/architecture.md](../docs/architecture.md)、判断理由は[ADR一覧](decisions/README.md)を参照してください。

## 現在地

- 設計段階。実装、package.json、テストはまだない。
- 2026-10-10に、構想・原則・構成・最初の対象言語・名前を決め、文書とADR-0001〜0005を作成した。
- npmの`inloop`は2026-10-10時点で未使用だった。名前の確保（プレースホルダーの公開）は未実施。
- 商標（J-PlatPat、USPTO）は未確認。

## 決まっていること

- AIが人にレビューを依頼するpush型。信頼境界に触れた変更は必須依頼にする（ADR-0001）
- 依頼票の構造はコードから決定的に生成し、AIの推測を混ぜない（ADR-0002）
- MCPサーバー＋MCP Appsとして、AIクライアントにホストされる。自作IDEは作らない。サーバーはLLMを呼ばない（ADR-0003）
- AIの文脈には参照・差分・短い列挙値だけを返す（ADR-0004）
- 最初の対象はTypeScript＋SQL。inloop自身もTypeScriptで書き、自分自身でレビューする（ADR-0005）

## 方向性はあるが未決のこと

- 作られるアプリのデスクトップ向け基盤はTauriを第一候補とする（軽さ、capabilitiesによる宣言的な信頼境界）。対応時期は未定。
- 解析エンジンの重い処理を、将来Rust製モジュールへ差し替える可能性。
- TypeScriptの型解決にGo版コンパイラ（TypeScript 7）を使えるか。外部から呼び出すAPIの状況は未確認。
- 最初に対応するサーバー側・画面側フレームワーク（候補: 画面はReact、サーバーはHonoかExpressのどちらか一つ）。
- ライセンス。
- [docs/review-protocol.md](../docs/review-protocol.md)の未決事項。

## 未検証事項

- 「AIがローカルのrepositoryを編集できる」ことと「MCP AppsのUIを表示できる」ことを、同じ画面で両立できるクライアント。
- CodexのクライアントアプリのMCP Apps対応。
- MCP Appsで、UI専用のツールをAIから見えなくできる範囲。
- 1回のレビューループのトークン消費量（設計上は数百トークン程度を見込むが、未測定）。

## 次の一手

1. npmで`inloop`のプレースホルダーを公開し、名前を確保する。
2. 最小のMCPサーバー（固定の依頼票を返すだけ）とMCP AppsのUIを作り、上記「未検証事項」の前2つを実際のクライアントで確かめる。
3. 結果をもとに、主に使うクライアントを決め、ADRに記録する。
4. 依頼票のデータ構造と状態遷移を確定する。
5. TypeScriptのシンボル解析と理解順の並べ替えを、inloop自身のコードを対象に作り始める。
