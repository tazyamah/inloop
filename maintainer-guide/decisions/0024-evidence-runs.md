# ADR-0024: 証拠（テスト・静的解析の結果）をinloopが実行して依頼票に入れる

- 状態: Accepted
- 日付: 2026-10-12
- Supersedes: なし

## 背景

依頼票の`evidence`は、解析エンジンの最初の版から常に空だった（ADR-0015）。人が読むときに「テストが通っているか」を見られるようにしたい。ただし結果をAIが書くと、構造にAIの推測や虚偽が混ざる（ADR-0002）。

## 決定

- `inloop.json`に省略できる`evidence`を足す。`{id, kind（test・static）, name, command}`の列で、`command`はシェルを通さずに実行する引数の列。`format`は1のまま。`id`の重複は拒否する。作業ツリーの`inloop.json`を使い、なければ基点のものを使う（`layers`と同じ）。
- `inloop evidence run [<id>...] [--repo]`が、リポジトリの最上位でコマンドを実行し、結果を`.inloop/evidence.json`（gitに入らない）に記録する。1つでも失敗なら終了コード1。時間切れ（10分）、起動できない、シグナルでの終了は`fail`。
- 記録には、実行したときの作業ツリーの指紋（HEAD、HEADからの差分、追跡していないファイルの中身）とコマンドを持たせる。依頼票を作るとき、設定した検査ごとに1件を`evidence`に入れる。
  - 結果があり、指紋とコマンドが今と同じなら、`pass`または`fail`。
  - 実行していない、コードやコマンドが変わった、結果が読めない、のどれかなら`missing`にして、名前に理由（「（未実行）」「（結果が今のコードのものではない）」）を足す。
- 検査と依頼票の結び付けは、検査単位（すべての依頼票に同じ証拠）にする。シンボルごとの結び付けは、この判断では足さない。

## 理由

- 結果をAIの引数にせず、inloopが動かして記録すれば、構造にAIの申告が混ざらない（ADR-0002）。AIが同じMacのシェルで`evidence.json`を書き換えうることは、既知の制約（ADR-0012、ADR-0013）と同じで、この判断では防がない。
- 検査のコマンドは`inloop.json`に置くので、変えると組み込みのルール`inloop-config`が当たり、必須の依頼になる（ADR-0022）。AIが検査を差し替えても人が気づく。
- 指紋で古い結果をfail-closedに`missing`にする。通った後にコードを変えても、通ったように見えない。
- テストとシンボルの結び付け（テストがimportするシンボルなど）は、解決できない場合の扱いも含め設計が大きい。先に検査単位で出して、使い勝手を見る。

## 影響

- 依頼票の形は変わらない（`evidence`に値が入るだけ）。記録の版は上げない。ADR-0024より前の記録の`evidence`は空のまま。
- 指紋の計算に`git`を数回呼ぶ。`request_review`のたびに、設定があるときだけ動く。
- `evidence`の`kind`は人への表示のためだけで、必須の依頼を左右しない。証拠の`fail`や`missing`で承認を妨げることもしない。

## 却下した代替案

- AIが結果を引数で渡す: 構造にAIの申告が混ざる（ADR-0002）。
- `request_review`のたびにinloopが検査を動かす: 遅く、依頼の呼び出しが長く止まる。
- テスト結果ファイル（JUnitなど）を読む: 誰が書いたか、いつのものかを確かめられない。

## 検証

`npm test`で、設定なしは空、実行前は`missing`、実行後は`pass`・`fail`、コード・追跡していないファイル・コマンドの変更で`missing`に戻ること、起動できないコマンドが`fail`、壊れた結果が`missing`、`inloop.json`の形の不正を拒否することを確かめる。実際のクライアントでの表示、画面での見え方は未検証。
