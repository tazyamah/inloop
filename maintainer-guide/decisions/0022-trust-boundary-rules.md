# ADR-0022: 信頼境界ルールをリポジトリの`inloop.json`に書き、必須の依頼をエンジンが作る

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（ADR-0001の「信頼境界ルールに該当する変更は、解析エンジンが自動で`required`の依頼を作る」の作り方を決める。ADR-0011の「inloopの設定」のファイル名と形式、ADR-0015の「最初の版で作らないもの」のうち信頼境界ルールと必須の依頼、ADR-0009が持ち越した「`required`の依頼の再依頼で種別と根拠のルールを決め直す方法」を決める）

## 背景

ADR-0001は、信頼境界ルールに該当する変更（認証、外部入力、秘密情報、外部通信、DB書き込みなど）について、解析エンジンが`required`の依頼を作り、AIはそれを取り消せないとした。ADR-0015の最初の版のエンジンは、`kind`を常に`optional`にしていた。決める必要があったのは次の点である。

- ルールをどこに、どの形で書くか。ADR-0011は「inloopの設定（信頼境界ルール、レイヤー対応ルール、使うinloopの版）をリポジトリに置き、commitする。ファイル名と形式は解析エンジンを作るときに決める」としていた。
- ルールがコードのどこに当たったかを、どう決定的に判定するか（ADR-0002）。
- 必須の依頼を、いつ、どの単位で作るか。AIが`request_review`を呼ばなければ、依頼は作られない。
- AIの判断で必須の依頼を省ける経路を、どう塞ぐか（AGENTS.md）。考えられる経路は、依頼しない、再依頼で種別を外す、会話から承認する、ルールのファイルを書き換える、の4つである。

## 決定

### 設定ファイル

- inloopの設定は、リポジトリ直下の`inloop.json`とする。commitする。`.inloop/`（実行時の記録、commitしない）とは分ける。
- 形式はJSONとする。最上位の項目は`format`（形式の版、今は`1`）と`boundaries`（信頼境界ルールの列）だけ。知らない項目、形の合わない値があれば、推測で読み飛ばさずに拒否する（綴りを誤ったルールが黙って効かなくなるのを防ぐ）。
- 使うinloopの版（ADR-0011）とレイヤー対応ルールは、この判断では足さない。足すときは、古い実装が知らない項目として拒否するので、取り違えは起きない。
- `inloop.json`がなければ、ルールは0件として扱う（`inloop-config`は働く、下記）。

```json
{
  "format": 1,
  "boundaries": [
    {
      "id": "db",
      "question": "データベースに書く値は、検証した入力だけから作っているか",
      "match": [
        { "import": "node:sqlite" },
        { "symbols": ["server/db.ts#Db"] }
      ]
    }
  ]
}
```

### ルール

- 1つのルールは`id`（英小文字・数字・`-`）、`question`（人への問い。依頼票の観点になる）、`match`（当て方の列。どれか1つに当たれば当たり）を持つ。
- 当て方は次の4種類とし、1つの項目に1種類だけを書く。
  - `{"import": "<モジュール>", "names"?: [...]}`: そのモジュールからimportした名前を使っている。`names`があれば、その名前（名前付きimportの元の名前、名前空間・既定のimportなら`x.名前`の名前）に限る。`node:fs`と`fs`は同じとみなす。`import("<モジュール>")`の動的importも当たる。importの宣言は型の解決でたどり、同じ名前の別の変数とは区別する。
  - `{"global": "<名前>"}`: リポジトリの外（標準ライブラリなど）で宣言された、または宣言までたどれない名前を使っている。`.`でつないだ名前（`process.env`）は、プロパティの参照の連なり（`process["env"]`を含む）と比べる。
  - `{"files": ["<glob>", ...]}`: そのファイルを変えた。`*`は`/`を含まない任意の文字列、`**`は任意の文字列。TypeScript以外のファイルにも使える。
  - `{"symbols": ["<シンボルID>", ...]}`: そのシンボルそのものを変えた、またはそれを直接使っている（ADR-0015の直接の依存。型としての参照を含む）。`*`と`**`を使える。
- 当て方を増やすのは、別のADRで決める。

### 何に当てるか

- 範囲の基点（ADR-0015）から作業ツリーまでに変わったファイル（追跡していない新しいファイルを含む）を対象にする。
- 空の行の変更は数えない。
- TypeScriptのファイルは、宣言ごとに`import`・`global`・`symbols`で判定する。変わった行を含む宣言のうち、内側の宣言（クラスのメソッドなど）に含まれない変わった行を持つものを、判定の単位とする。
- TypeScriptのファイルが`files`に当たるとき、またはファイルの最上位の文（宣言でもimport・exportの宣言でもない文、`serve(...)`など）が変わってルールに当たるときは、ファイル全体を1つの単位にする。シンボルIDはファイルのパスだけ（`server/index.ts`）にする。`files`は「このファイルは丸ごと境界」という指定なので、宣言ごとに分けない。
- TypeScript以外のファイルは、ファイルを1つの単位とし、`files`の当て方だけで判定する。シンボルIDはファイルのパスだけにする。
- 消したファイルは、`files`に当たれば単位にする。依頼票には、基点の中身を`<基点>:<パス>`として示す。
- 消したコード（宣言の削除）は、判定しない。
- ルールは、範囲の基点の`inloop.json`と作業ツリーの`inloop.json`の両方を読み、和を使う（同じ`id`なら当て方を合わせる）。AIがルールを消したり弱めたりしても、その範囲では消す前のルールも働く。

### 組み込みのルール`inloop-config`

- `inloop.json`を変えた（消した場合を含む）ときは、組み込みのルール`inloop-config`が当たる。`inloop.json`に書かなくても働き、`inloop.json`では同じ`id`を使えない。
- その依頼票には、今の`inloop.json`と、基点の`inloop.json`（`<基点>:inloop.json`）を並べる。変わった行だけでは、消したルールが見えないためである。

### 必須の依頼の作り方

- `request_review`の呼び出しのたびに、エンジンが範囲のすべての変更にルールを当てる。当たった単位ごとに、AIの依頼とは別に`required`の依頼を1件作り、同じ呼び出しのまとまり（ADR-0008）に入れる。
  - 観点は、当たったルールの`question`をルールの`id`の順に並べたもの。AIは書かない。
  - `triggeredBy`は当たったルールの`id`。対象のシンボルは、その単位1つ。依頼票の組み立ては、ADR-0015と同じ（指定したシンボルと直接の依存を理解順に）。
  - 1つの単位の依頼なので、行数の上限（ADR-0017）では断らない。
- すでに同じ単位の`required`の系列があり、最新の依頼票の、その単位のコードが今のコードと同じなら、作らない（状態は問わない）。コードが違えば、その系列の再依頼（枝番、ADR-0009）として作る。
- AIの依頼の依頼票でも、当たった単位のシンボルの`boundaries`に、ルールの`id`を入れる（画面で強調する）。
- `request_review`の`reviews`は空でもよい。空なら、必須の依頼だけを作る。必須の依頼もなければ、何も記録せずに「依頼がない」と返す。
- 戻り値は、必須の依頼があれば、テキストの末尾に`required:R6,R7`、structuredContentに`required`（IDの列）を足す。AIが人に伝えられるようにするためで、ADR-0004の短い列挙値の範囲に収まる。

### AIが省けないようにすること

- 依頼しない: `inloop check`（下記）が、承認されていない必須の依頼を示して失敗する。マージの条件（ADR-0001）は`inloop check`で確かめる。
- 再依頼で種別を外す: `required`の系列への`follows`は、種別・`triggeredBy`・対象のシンボル・観点を引き継ぎ、変えられない。`symbols`か`viewpoint`を違う値で渡せば、呼び出し全体を拒否する。固定データの依頼票（`fixture`、すべて`required`の見本）は、ルールから作ったものではないので対象外とする。
- エンジンが作り直す必須の再依頼は、`triggeredBy`をそれまでのルールとの和にする。コードを変えてルールに当たらなくしても、種別と根拠は残る。
- 会話から承認する: ADR-0017のとおり、`answer_review`は必須の依頼を記録しない。
- ルールを書き換える: 上の`inloop-config`と、基点のルールとの和で塞ぐ。
- AIが記録ファイルを直接書くこと、`~/.inloop/`を書き換えることは、ADR-0012、ADR-0013と同じく範囲外とする。

### `inloop check`

- `inloop check [--repo <dir>] [--range <範囲>]`を足す。範囲の既定は`HEAD`（作業ツリーの未commitの変更）。マージの前には、取り込む先（`main`など）を範囲に渡す。
- ルールに当たったすべての単位について、同じ単位の`required`の系列の最新の依頼が、承認済みで、その単位のコードが今のコードと同じであることを確かめる。1行に1単位で、`ok`、`missing`（依頼がない）、`pending`・`fixing`・`answering`・`held`（承認されていない）、`changed`（承認後にコードが変わった）を示し、1つでも`ok`でなければ終了コード1で終わる。
- 記録は書かない。必須の依頼を作るのは`request_review`だけとする。

## 理由

- JSONにしたのは、外部の依存が要らず、読み込みで形の全体を確かめられるからである（ADR-0009と同じ考え方）。コメントを書けないが、ルールごとの`question`が説明を兼ねる。
- 設定を`.inloop/`の中に置かないのは、`.inloop/`は記録でcommitしない一方、ルールはコードと一緒にレビューされ、commitされるべきだからである。
- 当て方を、モジュールのimport、標準の名前、ファイル、リポジトリのシンボルの4つに限ったのは、どれも型の解決とgitの差分だけで決まり、同じ入力から同じ結果になるからである（ADR-0002）。importの判定は、`node_modules`がなくても宣言の場所で決まる。パッケージの型の中まで当てる方法（`hono`の`app.post`など）は、`node_modules`がないと解決できず、黙って当たらなくなる（fail-open）ので、今は入れない。
- 単位を宣言にするのは、依頼票の単位（シンボル）と合わせるためである。宣言の外の文も単位にするのは、入口のファイル（`server/index.ts`の`serve(...)`など）の多くが最上位の文だからで、見落とすと穴になる。
- `files`の単位をファイル全体にしたのは、inloop自身に当ててみると、ルールのファイル（`src/engine/rules.ts`）の定数や型の1つ1つが必須の依頼になり、20件を超えたからである。
- 必須の依頼を単位ごとに1件にするのは、行数の上限で断られないようにするためと、承認と変更を単位ごとに突き合わせられるようにするためである。
- 作り直しをコードの一致で決めるのは、承認したときに見たコード（記録の依頼票）と今のコードを比べれば、承認後の変更を決定的に検出できるからである（docs/review-protocol.mdの未決事項のうち、必須の依頼について）。
- AIの依頼に`required`の種別を付け替えないのは、AIの観点と人への問い（ルールの`question`）が別のものだからである。
- 依頼しないことは、サーバーでは止められない（呼ばれなければ何もできない）。そのため、マージの前に人やCIが動かせる確認を用意した。

## 影響

- `request_review`のたびに、範囲のすべての変更を解析する。変わったファイルが多いと遅くなる（未計測）。
- AIの依頼に、AIが頼んでいない必須の依頼が加わる。同じ呼び出しの画面に並ぶ。
- `request_review`の`reviews`の最小件数が1から0になった。ツール定義の説明文が少し増える。
- 依頼票のシンボルIDに、ファイルのパスだけのもの（`inloop.json`、`server/index.ts`）と、`<基点>:<パス>`が加わる。依頼票の形は変わらないので、記録の版`v`は上げない（ADR-0009の基準）。古い実装も、これらを普通の依頼票として読む。
- 記録に`required`の依頼が現れる。古い実装は、会話からの承認を拒否する（ADR-0017から）ので、読み違えは起きない。
- `inloop new`の雛形に`inloop.json`（外部入力、データベース、秘密情報、外部通信、外部コマンド）を足した。inloop自身のリポジトリにも置いた。
- 当て方を特定のファイルに絞る指定はない。たとえば`fetch`を当てると、画面（`web/`）が自分のサーバーを呼ぶコードにも当たるので、雛形のルールには入れなかった。
- inloop自身の`inloop.json`で、この変更（`main`からの範囲）に当てると、必須の依頼は10件になった。
- ルールの品質が見落としの少なさを左右する（ADR-0001）。`import`と`global`の判定は、`require()`、文字列を組み立てた動的import、別のファイルから再exportした名前を追わない。

## 却下した代替案

- `inloop.config.ts`などのコードで書く: 読むためにコードを実行する必要があり、AIが書いたコードを評価の前に実行することになる。
- YAML: パーサーの依存が要る。
- ルールを`~/.inloop/config.json`（利用者ごと）に置く: リポジトリと一緒にレビューされない。行数の上限（感じ方の個人差）とは性質が違う。
- AIの依頼のうち、ルールに当たるシンボルを含むものを`required`に格上げする: AIが対象のシンボルを選ばなければ穴になり、AIの観点が人への問いを置き換える。
- 範囲のルールに当たった変更をまとめて1件の必須の依頼にする: 行数の上限を超え、承認後の変更を単位ごとに突き合わせられない。
- 作業ツリーのルールだけを使う: AIがルールを消せば、その範囲の必須の依頼が作られなくなる。
- 消したルールが見えるよう、`inloop.json`の差分を依頼票の新しい項目にする: 依頼票の形が変わる。基点の中身を並べれば、今の形で足りる。
- `inloop check`で必須の依頼を記録する: 確認のコマンドが記録を書くと、CIや人が動かしたときに依頼が増える。

## 検証

`npm test`で次を確かめる。

- `inloop.json`の形が合わない、知らない項目がある、`inloop-config`を使う、などを拒否すること
- `import`（名前付き、名前空間、動的import、同じ名前の別の変数との区別）、`global`（`process.env`、`process["env"]`、同じ名前の変数との区別）、`files`、`symbols`の当て方
- 変わっていない宣言には当てないこと。クラスのメソッドを変えたら、クラスではなくメソッドに当てること
- 宣言の外の文、TypeScript以外のファイル、消したファイル、`inloop.json`の変更（基点の中身を並べる）
- 必須の依頼は、行数の上限で断らないこと
- 基点のルールを作業ツリーで消しても、その範囲では当たること
- `request_review`で、当たった単位ごとに必須の依頼が同じまとまりに加わり、戻り値に示されること。コードが同じなら作り直さず、違えば枝番の再依頼になること。`reviews`が空でも必須の依頼を作れること
- 必須の系列への`follows`で、種別と対象を変えられないこと
- `inloop check`が、依頼がない・承認されていない・承認後に変わった単位を示して失敗し、すべて承認済みなら成功すること

実際のクライアントで、AIが必須の依頼を人に伝えるか、`inloop check`を動かすかは未検証である。
