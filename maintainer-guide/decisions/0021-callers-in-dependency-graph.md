# ADR-0021: 依頼票に呼び出し元を1段だけ残し、依存の図の右の列に出す

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（ADR-0020で決めなかった「呼び出し元を図に入れるか」を決める。ADR-0015の`steps`は直接の依存までのまま）

## 背景

ADR-0020で依存の図を作ったとき、呼び出し元（影響範囲）を入れるかは利用者の判断を待っていた。利用者は「呼び出し元入れる。既存のコードは畳む、図は先頭」と答えた（2026-10-11）。後の2つはADR-0020の形のまま。

## 決定

- 依頼票に`callers`（`symbol`、`file`、`startLine`、`code`の列）を足す。AIが指定したシンボルと、変わった（`added`・`modified`）シンボルを、呼び出す（`new`を含む）リポジトリの宣言を、1段だけ探す。
  - 型として参照しているだけの宣言は入れない。型を変えたとき、使っている側がすべて入って数が膨らむため（inloop自身で、`ReviewPacket`を変えた作業ツリーで`ReviewStore.create`を依頼すると、型も数えれば15件、呼び出しだけなら1件だった）。
  - `steps`に入ったシンボル、それを含む宣言・それに含まれる宣言（クラスとそのメソッド）は除く。ほかの宣言を含む宣言（クラス）は数えず、中のメンバーの側で数える。
  - 呼び出し元の呼び出し元はたどらない。数の上限は設けない（画面の側で省かない、R4）。
  - 並びは、ファイルのパスと位置の順。
- 呼び出し元から対象への関係は`edges`に入れる（`from`が呼び出し元）。`edges`の`to`は常に`steps`のシンボル、`from`は`steps`か`callers`のシンボル。
- `callers`を`steps`に混ぜないのは、理解順の対象ではなく影響範囲だからである。行数の上限（ADR-0017）にも数えない。
- 読み込みで、`steps`と重なる呼び出し元、`edges`の`from`が`steps`にも`callers`にもない関係を拒否する。`callers`のない依頼票（この判断より前の記録）は、そのまま読む。記録の版は1のまま（古い実装は知らない項目として捨て、`edges`の`from`が`steps`にないことで拒否する。拒否はするが、読み違えはしない）。
- 画面: 依存の図で、呼び出し元を並べたシンボルの右に1列で、点線の枠で出す。コードは依頼票の「対象」の後の「呼び出し元」に並べ、既定で畳む。図の箱を押すと開いてそこへ移る。

## 理由

- 変更を確かめるとき、変えたものをどこが呼んでいるかは、直接の依存と同じくらい判断に要る。
- 1段に限るのは、図を一度に見渡せる大きさに保つため。さらに先は、呼び出し元を対象にした別の依頼で見られる。
- 名前が本文に現れる宣言だけを解析するので、プロジェクト全体を見ても、inloop自身で1回の依頼が0.4〜0.6秒だった。

## 影響

- 依頼を作るとき、プロジェクトのすべての宣言の本文を見る。対象の名前を含む宣言だけ、参照を求める。
- ADR-0020の実装（古い実装）は、呼び出し元のある依頼票を「依頼票の形が不正（edges.N）」として拒否する。新しい実装に上げれば読める。
- 動的な呼び出し（コールバック、イベント）からの呼び出し元は見つからない。

## 却下した代替案

- 型として参照している宣言も入れる: 型を変えると数十件になる。
- 呼び出し元を`steps`に入れる: 理解順の対象と混ざり、行数の上限にも数えることになる。古い実装が普通の対象として読んでしまう。

## 検証

`npm test`で、指定したシンボルと変わったシンボルの呼び出し元を1段だけ探すこと、`new`ではコンストラクターの呼び出し元になること、クラスを含む宣言と並べたシンボルを除くこと、読み込みで重なりと関係の端を確かめることを確かめる。`INLOOP_UI_E2E=1 npm test`で、図の右の列に点線の枠で出し、コードを畳み、箱を押すと開くことを確かめる。

実際の依頼で役に立つかは未検証。
