# ADR-0020: 依頼票に「使う関係」を残し、画面の先頭に依存の図を出す。変わっていない依存のコードは畳む

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（ADR-0009の依頼票の項目に`edges`を足す。ADR-0015の「並べるのは直接の依存まで」は変えない）

## 背景

依頼票は、理解順に並べたシンボルのコードを上から全部見せるだけだった。どれがどれを使っているかは、解析エンジンが求めていたが（`src/engine/build.ts`の`deps`）、並び順に使ったあと捨てていた。

利用者は、R6（5シンボル、54行）くらいが一度に認識できる限界と感じ、行数の上限（ADR-0017）を設けた。あわせて「データの流れなどの図で判断できるようになれば、上限は不要になるかもしれない」とメモしていた（handoffの次の一手の保留項目）。

決める必要があったのは、何を図にするか（データの流れか、呼び出し関係か、影響範囲か）、図の元を依頼票に残すか画面で求めるか、コードの見せ方を変えるか、である。

## 決定

### 依頼票の項目

- `ReviewPacket`に`edges`（`{from, to, kind}`の列）を足す。`from`が`to`を使う。`kind`は`call`（呼び出し）・`new`（コンストラクター）・`type`（型としての参照）・`inherit`（継承・実装）。
- 両端は必ず`steps`のシンボルとする。並べたシンボルどうしの関係は、依存として並べたものの中の呼び出しも含めて残す。ただし、それをたどって新しいシンボルを並べはしない（ADR-0015の直接の依存まで、は変えない）。
- 同じ2つの間に別の種類の使い方があれば、別の項目にする。並びは、使う側・使われる側の理解順、種類の順（同じ入力からは同じ並び）。
- 解析エンジンが作る。AIは関与しない（ADR-0002）。固定データの依頼票にも、合成した関係を1本入れる。
- 読み込みで形を確かめ、両端が`steps`にない関係は「依頼票の形が不正（edges.N）」として拒否する。
- `edges`のない依頼票（この判断より前の記録）は、そのまま読む。関係を補わない。
- 記録の版`v`は1のまま（ADR-0009の基準）。すでにある行はそのまま読め、古い実装は知らない項目として`edges`を捨て、これまでの画面を出すだけで、意味を読み違えない。

### 画面

- 依頼票の「対象」の前に「依存の図」を置く。`edges`のない依頼票では出さない。
- 箱は`steps`の各シンボル。名前、理解順の番号、変更の印（追加・変更は行数、変わっていない）を出す。色は変更の印、太枠はAIが指定した対象。未解決の参照を含むシンボルには印と件数を出す（未解決の参照の`file:line`が、そのシンボルの行の範囲にあるもの）。
- 矢印は使う側から使われる側へ。使われる側を左に置く（依存の深さで列を分ける）。呼び出しと`new`は実線、型と継承だけなら破線。同じ2つの間の線は1本にまとめ、種類は線の説明に出す。列を飛ばす線と循環の線は、箱の下を回す。
- 箱を押すと、そのシンボルのコードへ移る（畳んであれば開く）。各シンボルの見出しの下に「使う」「使われる」を出し、押すとそのコードへ移る。
- 図は外部のライブラリを使わず、SVGを自前で描く（画面は外部依存のない単一HTML）。
- 変わっていない依存（`change`が`unchanged`で、AIが指定していないもの）のコードは、既定で畳む。見出しと「コードを表示（N行）」は常に出し、押せば全行出る。省くのではなく畳むだけ（R4の「画面の側では省かない」を守る）。

### 名前

- この図は「依存の図」と呼び、「データの流れ」とは呼ばない。値がどの引数からどこへ渡るかは、今の解析エンジンでは追えない。

### 今回は決めないこと

- 呼び出し元（影響範囲）を図に入れるか。今の解析エンジンは直接の依存だけを求める（ADR-0015）。入れるなら、変わったシンボルを使っている側を1段だけ逆引きすることになる。
- 行数の上限（ADR-0017）の数え方。図と折りたたみで判断できるようになったかを、実際の依頼で確かめてから決める。第一候補は、畳んである変わっていない依存の行を数えないこと。

## 理由

- 図の元を依頼票に残すのは、依頼票の構造を解析エンジンが決めるため（ADR-0002）。画面で推し量って線を引くと、エンジンが確かめていない関係を見せることになる。
- 記録に残すので、後から画面を開いても、依頼したときの関係が見える（記録として残す、という方針）。
- 呼び出し関係は、型の解決ですでに求めており、決定的に作れる。データの流れは作れないので、作れるふりをしない。
- 変わっていない依存を畳むのは、人が読む量を変わった部分に寄せるため。どの依存が何に使われているかは図で分かる。

## 影響

- 依頼を作るとき、並べたシンボルすべてについて参照を求めるようになった（これまでは指定したシンボルだけ）。解析の時間は、並べた数に比例して増える。
- 画面の大きさは約621KB（約11KB増）。
- 画面で、変わっていない依存の行は、開くまでクリックで位置をコピーできない。
- 古い実装で新しい記録を読むと、図のない画面になる。

## 却下した代替案

- 画面で`steps`のコードから関係を推し量る: エンジンが確かめていない関係を見せることになる。
- グラフ描画のライブラリ（mermaid、elkなど）を入れる: 単一HTMLが大きくなり、並びが決定的か確かめにくい。今の大きさの依頼票なら、列に分けるだけで読める。
- 変わっていない依存を依頼票から外す: R4の指摘のとおり、見えない部分ができる。

## 検証

`npm test`で次を確かめる。

- 並べたシンボルどうしの使う関係を、種類とともに残し、依存どうしの関係も含めること。両端が依頼票のシンボルであること
- 両端が依頼票にない関係、知らない種類を、読み込みで拒否すること。`edges`のない依頼票を読めること

`INLOOP_UI_E2E=1 npm test`で次を確かめる。

- 依存の図に、すべてのシンボルが箱で、記録した関係だけが線で出ること。使われる側が左にあること。箱を押すとそのコードへ移ること
- 変わっていない依存を畳み、図の箱やボタンで開け、また畳めること。指定した対象は畳まないこと

図で判断できるようになったか、行数の上限を見直せるかは、実際の依頼では未検証。
