# ADR-0012: MCP AppsのUIを表示できないクライアント向けに、同じUIをブラウザで開く

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（ADR-0003が「用意する」とした代替経路の形を決める）

## 背景

ADR-0003は、MCP Appsに対応しないクライアント向けに、同じUIをローカルのブラウザで開く代替経路を用意するとしていたが、形は決めていなかった。

2026-10-11に、Claudeデスクトップアプリの中のClaude Codeで確かめると、inloopのツールは呼べたが、レビューUIは会話に表示されなかった。利用者はこのクライアントで手元のMacを直接扱って開発したいので、UIを出す経路が必要になった。

UIをブラウザで出すと、次の点がMCP Appsと変わる。

- UIからの`sendMessage`で会話にメッセージを入れられない。回答はAIが取りに行く必要がある。
- UIを開く場所（URL）を誰かが知る必要がある。

## 決定

- 起動時に`--ui browser`を指定したときだけ、サーバーは127.0.0.1でHTTPを待ち受ける。ポートは空いているものを使う。指定がなければ、これまでと同じ（MCP Appsだけ）。
- 起動ごとに推測できない鍵を作り、すべての要求にURLの`t`として求める。Hostヘッダーが`127.0.0.1`か`localhost`の、そのポートでなければ拒否する。鍵はログに出さない。
- HTTPから呼べるのはUI専用のツール（`inloop_get_request`、`inloop_submit`、`inloop_reopen`）だけとする。AIが呼ぶツールは呼べない。受け付けるのは`application/json`の要求だけとする。
- 画面は、ブラウザ側の小さなホスト（`dist/ui/browser.html`）がMCP Appsのホストの役を務め、既存のレビューUI（`dist/ui/review.html`）をiframeに読み込む。UIのコードは共通にする。
- `request_review`は、テキストで`R1 R2 pending <URL>`、structuredContentで`{ids, url}`を返す。URLは、その呼び出しで最初に作った依頼の画面を指す。AIはURLを人に示すか、ブラウザで開く。
- `get_review_result`に`wait`（秒、最大1800）を足す。指定した依頼がすべて回答されるまで待つ。待ち始めに未回答の依頼がなく、保留・回答待ちの依頼があれば、人が未回答に戻して答え直すまで待ち、新しい回答がなければ`no change`を返す。時間切れのとき、未回答の依頼は`R2 pending`として示す。
- ブラウザの経路で起動したときは、AIから見えるツールの説明文を、URLを開くこと・`wait`を使うことが分かる形に変える。
- UIの「会話に送る」は、ブラウザのホストでは何も送らず、「回答を記録しました」と表示する。
- 標準入力が閉じたら、HTTPを閉じてプロセスを終える。

## 理由

- UIのコードを共通にすれば、MCP Appsで確かめた操作（行起点のコメント、まとめての回答、未回答に戻す）がブラウザでもそのまま使える。
- ブラウザには会話へ入れる手段がないので、AIが待つ形にした。`wait`がなければ、人が会話に戻って「回答した」と伝える必要がある。
- 鍵とHostの確認は、同じ端末のほかのWebページやプロセスから回答を送られるのを防ぐためである。
- URLの鍵はAIの文脈に入るので、AIが自分で回答を送ることは技術的には防げない。ただし、AIは同じ端末のシェルで記録ファイルを直接書けるので、危険の種類は増えない。AIによる自己承認を防ぐことは、この判断の範囲外とする。

## 影響

- AIの文脈: 依頼の戻り値にURL（約55文字）が増える。AIから見えるツール定義は、ブラウザの経路でも1500文字未満（テストで確認）。MCP Appsの経路では、`get_review_result`の引数に`wait`が増えた分だけ増える。
- ブラウザの画面は会話の中に出ない。人は別の画面で回答する。
- 同じ名前のサーバーをClaude Desktopの設定とClaude Codeの両方に登録すると、Claudeデスクトップアプリの中のClaude Codeでは、Claude Desktopの設定のほうが呼ばれた（2026-10-11）。ブラウザの経路で登録するときは、別の名前にする。
- 対象のリポジトリを依頼ごとに決める変更（ADR-0010）を入れるときは、URLとHTTPの呼び出しに対象を含める。

## 却下した代替案

- サーバーがOSの既定のブラウザを自分で開く: URLをAIに渡さずに済むが、毎回ブラウザのタブが増え、どの会話の依頼かが人に分かりにくい。必要になれば足す。
- 鍵をAIに渡さず、人だけが知る方法で渡す: AIがアプリ内のブラウザを操作する場合は、どのみちAIが画面を操作できる。
- ブラウザ用に別のUIを作る: 同じ操作を二重に作ることになる。

## 検証

`npm test`で次を確かめる。

- `request_review`がIDとURLを返し、URLが短いこと
- 鍵の違い・欠落、Hostの違い、JSON以外の要求、AIのツールの呼び出しを拒否すること
- `wait`が、回答の記録ですぐ返り、時間切れでは未回答を示し、保留・質問の後は答え直しまで待つこと
- `--ui browser`の実プロセスが、URLを返し、鍵をログに出さず、標準入力が閉じたら終わること

実際のクライアントでの確認（2026-10-11、Claudeデスクトップアプリの中のClaude Code）: 依頼2件のURLを利用者が普通のブラウザで開き、R1を保留、R2を質問で送信すると、待っていた`get_review_result`に2行が届いた。R2を未回答に戻して承認すると、記録に残った（このときは待ち受けが答え直しを待たずに戻る不具合があり、上の決定のとおり直した。直した後の動作は自動テストだけで確かめている）。アプリ内のブラウザ（ブラウザペイン）は、利用者の画面に表示されなかった。
