# ADR-0028: 信頼境界ルールにSQLのテーブルでの当て方（`table`）を足す

- 状態: Accepted
- 日付: 2026-10-12
- Supersedes: なし（ADR-0022の「当て方を増やすのは、別のADRで決める」に従う。ADR-0026の`tables`の材料を使う）

## 背景

ADR-0026は、依頼票に読む・書くテーブルを出したが、信頼境界ルールで「`orders`への書き込み」を指定する手段がなかった。`import "node:sqlite"`では、どのテーブルに触っても同じ問いになる。

## 決定

- ルールの`match`に、5つ目の当て方を足す: `{"table": "<名前>", "access"?: ["read"|"write"|"schema", ...]}`。`format`は1のまま。
  - `table`は大文字小文字を区別せず、`*`を使える。`access`を省くと、どの種類でも当たる。
  - 判定の材料は、ADR-0026の字句によるテーブルの取り出し。変わった宣言（と変わった最上位の文）の`prepare`・`exec`の文字列リテラルのSQLと、その宣言が直接使う宣言（ADR-0022の`symbols`と同じ範囲）のSQLを調べる。つまり、SQLを実行する関数を呼ぶだけの宣言にも、1段だけ当たる。
  - 動的なSQL（`prepare`の引数が文字列として読めない）を含む単位には、`table`の当て方を持つルールを当てる。触るテーブルが決められないので、当たらないとするより見落とさない側に倒す。そのときは、問いにルールのidと理由（`動的なSQLを含み、触るテーブルを決められない`）を足す。
- `table`の当て方を持つルールがなければ、SQLは調べない（既存のルールの速度は変わらない）。

## 理由

- テーブルは、データベースの信頼境界を指す自然な単位で、依頼票の`tables`と同じ言葉でルールを書ける。
- 動的なSQLを当てるのは、「解決できない参照を推測でつながず未解決と明示する」（AGENTS.md）と、「信頼境界のレビューを省ける経路を作らない」（ADR-0001）の両方に合う。推測で「当たらない」とはしない。

## 影響

- 記録の版は上げない。古い実装は、知らない当て方を含む`inloop.json`を拒否する（ADR-0022）。`minVersion`で防げる。
- 列、ORM、2段以上の間接、別の変数に入れたSQL文字列は追わない。変数に入れた文字列は動的として扱われ、`table`のルールに当たる。
- 雛形のルールには足していない（テーブルはアプリごとに違う）。

## 却下した代替案

- 動的なSQLには当てない: 動的なSQLこそテーブルを検証できず、見落とす穴になる。
- 列での当て方: 字句の解析では列の別名やスキーマの対応が決まらない。必要になってから別のADRで決める。
- 呼び出し先を何段もたどる: 依頼票の依存の範囲（直接の依存まで、ADR-0015）と食い違う。

## 検証

`npm test`で、テーブル名（大文字小文字）と種類での当たり方、`access`を省いたとき読むSQLにも当たること、SQLを実行する関数を直接使う宣言に当たること、動的なSQLの単位に当たって理由が問いに入ること、不正な形の拒否を確かめる。
