# ADR-0046: 命名規則のlintで、HTTPの入口（ユースケース）から、データ（テーブル・列）とテストへ結ぶ図を作る

- 状態: Accepted
- 日付: 2026-10-13
- Supersedes: なし（ADR-0002の「依頼票の構成要素にデータの流れ」のうち、値の流れは作らない結論は変えない。ADR-0045の検査に、別の目的の規則`uc-*`を足す）

## 背景

利用者の依頼（2026-10-13）: 生成できる図の種類を増やしたい。ユースケース図と、そこからリンクして、どういうデータが使われ、どういうテストが書かれているかが分かるものにしたい。lintを厳しめにして、変数の命名規則などから、コードと紐づいた形の図を作れないか。

現状（[docs/diagrams.md](../../docs/diagrams.md)）の図は「依存の図」だけで、ER図とデータフロー図は作っていない。値の流れは今の解析（呼び出し関係とSQL文字列）では追えないため。

実際のコードと解析エンジンで、結べるかを確かめた（標準の雛形に`inloop generate scaffold task …`を足した、8つのルートのアプリ）。

| 結びたいもの | 今の解析でできるか | 根拠 |
|---|---|---|
| ユースケース（入口）を、コードから一意に決める | できる。ただし**名前ではなく、登録のリテラル**から。ハンドラーは無名関数で、シンボルIDを持たない | `app.get("/:id", (c) => …)`の`"/:id"`と、`app.route("/api/tasks", tasksRoutes(db))`の`"/api/tasks"`は、構文とリテラルだけで読める。`PUT /api/tasks/:id`のように完全なパスに決まる |
| 入口からデータ（テーブル・列）へ | できる | ハンドラーの中と、呼ぶ関数（2段まで）のSQL文字列を、ADR-0026・0030・0031の読み方で取る。`DELETE /api/tasks/:id`は`removeTask → isDone`経由で読む列まで出た |
| 入口からテストへ | できる。ただしADR-0025の**シンボル参照では結べない** | テストは`tasksRoutes`を呼ばず、`app.request("/api/tasks/${id}", { method: "PUT" })`というHTTPで動かす。シンボルの参照はなく、結べるのは**パスとメソッドのリテラル**だけ |
| 入力の値が、どの列に入るか（値の流れ） | できない | `parse()`が検証した値が`run(...values)`の`?`の並びに入る対応は、変数の名前（列名と同じ）に頼る推測になる。関数をまたぐと追えない。作ると、確かめていない線を引くことになる（ADR-0002、AGENTS.md） |
| テストが何を確かめているか（assertの内容、成功・失敗） | しない | 要求を送っていることしか言えない。結果（成功・失敗）はADR-0024の検査単位の結果で、入口ごとには結び付かない |
| 利用者の言葉のユースケース名（「タスクを完了にする」） | できない | コードにない情報。名前を人やAIが書くと、構造に推測が混ざる |

結論: 「入口 → データ → テスト」は、**命名規則とリテラルの形を厳しく検査すれば、確実に結べる**。「値の流れ」と「ユースケースの意味」は結べない。変数の命名規則が効くのは一部で、効かせたいのは、変数ではなく**入口の登録とテストの要求の書き方**である。

## 決定

### ユースケースの定義

ユースケース = HTTPの入口1つ = `メソッド 完全なパス`（例: `PUT /api/tasks/:id`）。`inloop.json`の`usecases`（`routes`: 入口を書くファイルのglob、`tests`: テストのファイルのglob）で、解析する範囲を指す。`usecases`を書かないアプリには何も変わらない。`format`は1のまま。

### 命名規則と、新しいlintの規則（`inloop lint`、`inloop check`）

`usecases`を書いたアプリだけに、次の4つが働く。違反すると、ADR-0045の`secure`の検査と同じく、終了コード1にする。例外の書き方（`secure.allow`など）は作らない（結び付けに穴を空けないため。`usecases`そのものを消す変更は、`inloop-config`で必須の依頼になる）。

- `uc-app-name`: `routes`のファイルのHonoの変数は`const app = new Hono()`の名前にする。
- `uc-route-literal`: 入口は`app.get|post|put|patch|delete("/…", …)`で、パスは`/`で始まる文字列リテラル。マウントは`app.route("/接頭辞", xxxRoutes(db))`の形。`app.on`・`app.mount`・`app.basePath`・`app.all`は使わない。
- `uc-route-duplicate`: 完全なパスとメソッドが同じ入口を2つ作らない。
- `uc-test-request`: `tests`のファイルの`app.request(…)`は、パスを文字列・テンプレート・`+`でつないだ式（式の部分は`${}`）で書き、メソッドは省略（GET）・`{ method: "POST" }`・`json("POST", …)`（最初の引数がHTTPメソッドの呼び出し）のどれかで書く。

雛形（サーバー向け）の`inloop.json`に`usecases`を入れ、`AGENTS.md`に規則を足す。雛形と`inloop generate scaffold`の生成物は、この規則に従う（テストで確かめる）。

### 結び付け（`src/engine/usecases.ts`）

- 入口: 上の形の登録を集め、`app.route`でマウントした宣言（`tasksRoutes`など）の名前から接頭辞をつなぐ（4段まで）。どこからもマウントされていない宣言は、接頭辞なしの根として扱う。
- データ: ハンドラーの引数のコードの`prepare`・`exec`の文字列と、ハンドラーが呼ぶ宣言（ADR-0030の`INDIRECT_DEPTH`と同じ、呼び出し2段）の文字列を、`tablesOf`で読む。呼び出しの先のものは`via`つき。動的なSQLは未解決。
- テスト: `app.request`の（メソッド, パス）が、同じメソッドで、区切りの数が同じで、リテラルが等しい入口に結ぶ。入口の`:名前`はどの値にも合い、テスト側の`${}`は入口の`:名前`とだけ合う。複数に合うときは、リテラルが一致した区切りが最も多い入口だけ。どれにも合わなければ、結ばずに`inloop usecases`が示す。テストの名前は、囲む`test("…")`・`it("…")`の最初の引数。

### 依頼票への追加項目

`ReviewPacket.usecases?: ReviewUseCase[]`（省略できる。記録の版は上げない）。`{ id, symbol, file, line, tables[], tests[] }`。

- `symbol`は、画面で押したときに移る先で、依頼票に並んだシンボル。入口を登録している宣言が並んでいればそれ、並んでいなければ、入口のコードから呼び出しでたどれる宣言のうち、並んだもの。どちらも並んでいない入口は載せない（依頼の対象につながる入口だけ）。
- `tables`は`ReviewTable`から`symbol`を除いた形。`tests`は`{ name, file, line }`（同じテストが同じ入口に複数回要求しても1件）。
- `usecases`を書かないアプリ、ADR-0046より前の記録には、項目がない（「調べていない」）。`inloop.json`に`usecases`があって入口がつながらない依頼は`[]`。
- 記録を読むときの検査（`store.ts`の`packetSchema`）に、形と、`symbol`が並んだシンボルであることを足す。

### 図の見せ方

依頼票の画面に「ユースケース図」を足す（`src/ui/usecases.ts`、依存の図の前）。左: テスト、中: 入口、右: テーブル。矢印は、テスト→入口、入口→テーブル。入口→テーブルは、書くなら青の太線、読むなら灰色、スキーマなら破線（同じ入口と同じテーブルに複数の使い方があれば、強い方）。入口の箱を押すと、その入口を登録しているコードへ移る。テストの見つからない入口は、箱の右上に赤い点と「テストなし」。図の下に、同じ内容の一覧（列、経由、テストのファイル:行）を出す。図の説明に、値の流れとテストの確認内容は示さないことを書く。

`inloop usecases [--repo <dir>]`で、同じ一覧を端末に出す（違反があれば終了コード1）。

## 理由

- ユースケースを入口にしたのは、コードの中で名前を持たずに、リテラルとして確定しているのが入口だけだから。関数や変数の名前を厳しく決めても、ハンドラーが無名関数である限り、名前は入口を指せない。逆に、入口の登録とテストの要求の書き方を縛れば、構文だけで決まる。
- テストをHTTPの要求で結んだのは、このアプリのテストの書き方（雛形も生成物も、`app.request`）に合っているから。ADR-0025の「呼び出す・newするシンボル」は、HTTP越しのテストには働かない。
- 検査を`inloop lint`に入れたのは、ADR-0045と同じ理由（アプリに検査器を置くとAIが書き換えられる。`inloop check`がマージの条件に含める）。例外を作らないのは、例外があると、図の「テストなし」「データなし」が信用できなくなるため。
- 値の流れを作らないのは、確かめていない線を引かない原則（ADR-0002）。図が示すのは「入口のコードが触るテーブル」と「入口を動かすテスト」で、「この入力がこの列に入る」は示さない。
- 既定を「`usecases`を書いたアプリだけ」にしたのは、既存のアプリへの影響を小さくするため（`inloop check`は検査を動かすので、既存のアプリで新しい違反が出る経路を作らない）。
- 依頼票の項目を追加で済ませたのは、ADR-0020・0021・0026と同じ（省略できる項目、記録の版は1）。
- 構造に、AIが書いた文を混ぜない。ユースケースの名前が`METHOD /パス`なのは、そのため。

## 影響

- 古いinloopは、`usecases`のある`inloop.json`を「形が不正」として拒否する（`format`は1のまま。ADR-0031と同じ影響）。`inloop update`で防げる。`minVersion`は、まだ版が決まっていないので、雛形には入れていない。
- `inloop lint`のコード検査は、`usecases`のあるアプリで、`routes`と`tests`のファイルに規則が増える。標準のサーバー向けの雛形と`scaffold`の生成物は、違反なし（テスト済み）。
- `--standalone`・`--sync`・`--desktop`の雛形には入れていない。入口の書き方が違う（`--desktop`はHonoの親アプリが別の形）か、テストの要求が多い（`--sync`）ため、使ってみてから決める。`inloop.json`に`usecases`を足せば、手で有効にできる。
- テストのない入口は、違反にしていない（依頼票と`inloop usecases`に「テストなし」と出す）。人が見て、足りなければ足す。違反にするかは、実際に使ってみてから決める。
- 結び付くのは`app.request`を通すテストだけ。Playwrightなどのブラウザ越しのテスト、`fetch`でサーバーを起動して叩くテストは結ばない（`uc-test-request`は`app.request`の形だけ検査する）。
- `inloop evidence`のテスト結果（成功・失敗）は、入口ごとには結び付けていない。
- 解析の範囲は、Honoと`app`という名前。Express、Fastifyなどのフレームワークは、別の解析が要る。

## 却下した代替案

- 変数や関数の命名規則（`createTask`のような名前）でユースケースを決める: ハンドラーが無名関数で、テストは名前を参照しない。名前を縛っても、コードとテストの結び付きは守られない。
- `app.get("/", createTask)`のように、ハンドラーに名前を付ける規則を足す: 雛形と生成物の変更が大きく、既存のアプリへの影響も大きい。入口の登録の形を縛れば足りる。
- 値の流れ（入力→列）を、列名と変数名の一致から作る: 確かめていない線になる。
- テストの名前に`UC:`のような印を付けさせる: AIが書いた印を信じることになり、実際に動かしている入口と食い違いうる。要求のリテラルから決める。
- 違反に例外を認める（`secure.allow`の流用）: 「テストなし」「データなし」の信頼が下がる。
- 全アプリで既定で有効にする: 既存のアプリの`inloop check`が、設定を変えずに失敗するようになる。
- ユースケース図を、依存の図の中に混ぜる: 結び付けるものが違う（呼び出し関係と、HTTPの入口・テーブル・テスト）。

## 検証

`npm test`の`test/usecases.test.mjs`で次を確かめる。

- マウント先の接頭辞つきの入口の見つけ方、直接・経由つきのSQLの表と列、テストの結び付け（`${}`、リテラル優先、結ばれない要求）
- 4つの規則が、書き方ごとに違反を見つけ、`usecases`のないアプリには働かないこと。`inloop lint`・`inloop usecases`の終了コード
- 依頼票に、並んだシンボルにつながる入口だけが載り、`symbol`が並んだシンボルであること
- 標準の雛形と`scaffold`の生成物で、違反なし、8つの入口のうちテストのないのが1つ（`/api/health`）、`POST /api/tasks`が`tasks(done, due, title)`を書き、テストに結ぶこと
- `inloop.json`の`usecases`の形の検査

`INLOOP_UI_E2E=1 npm test`で、ユースケース図の描画（左・中・右の並び、テストなしの表示、入口を押してコードへ移ること）を、実ブラウザ（Chromium）で確かめる。画像は、`scripts/diagram-samples.mjs`で作る（`docs/diagrams/usecases-light.png`）。

未検証: 実際のClaude Codeの会話で、AIが規則に反するコードを書いたときに、`inloop lint`の出力から自力で直せるか。既存のアプリでの偽陽性（`usecases`を書いた場合）。`--standalone`・`--sync`・`--desktop`での使用。macOSでの実行。
