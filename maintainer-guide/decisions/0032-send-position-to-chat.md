# ADR-0032: クリップボードが使えないホストでは、行クリックの位置を会話に送る

- 状態: Accepted
- 日付: 2026-10-12
- Supersedes: なし（ADR-0018の「行のクリックは、いつでも位置のコピーにする」に、コピーできないホストでの扱いを足す）

## 背景

ADR-0017・0018で、議論は会話で行い、画面の行をクリックして位置（`R7 server/app.ts#createApp#L21`）をコピーし、会話に貼ることにした。Claude Desktopの通常の会話（MCP Appsのiframe）では、クリップボードへのコピーが許されず、位置を手で写すしかなかった（2026-10-12、利用者の確認）。承認ボタンは、記録した回答を`sendMessage`で会話に送れており、その方法は動いている。

## 決定

- 行のクリックで、クリップボードにも選択してのコピーにも失敗したときは、`sendMessage`で位置を会話に送る。
  - 本文は`[inloop] 位置の指定: <位置>（この位置についての指示が続きます。次の発言を待ってください）`。依頼ID・参照だけで、コードや依頼票の中身は含めない（ADR-0004）。
  - 送れたら「会話に位置を送りました」、送れなければ従来どおり「コピーできませんでした。手で写してください」と位置を出す。
- コピーできるホスト（ブラウザの経路、Playwrightなど）は、これまでどおりコピーだけで、会話には送らない。

## 理由

- 利用者の操作を、貼り付けから、クリックだけに減らす。承認と同じ経路なので、新しいホストの機能に頼らない。
- コピーできるときに会話へ送らないのは、クリックのたびにAIの手番が始まるのを避けるため。

## 影響

- 送ったメッセージでAIの手番が始まる。本文で「次の発言を待つ」ように書いたが、AIが従うかは未確認。
- 範囲の指定（Shift+クリック）は、クリックのたびに送る。1行目を送ったあとに範囲を広げると、位置が2回送られる。

## 却下した代替案

- `updateModelContext`で、見えない文脈として渡す: 利用者の画面に出ず、AIが使うかも保証されない。
- いつでも会話に送る: コピーできるホストで、クリックごとにAIが動いて邪魔になる。

## 検証

実際のClaude Desktopでの動作は未検証。コピーできるホストでの動き（コピーのみ）は、既存のE2Eのまま。このセッションではPlaywrightのブラウザがなく、`INLOOP_UI_E2E=1 npm test`は実行できなかった。
