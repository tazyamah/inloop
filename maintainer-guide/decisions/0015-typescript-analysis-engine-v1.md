# ADR-0015: 解析エンジンの最初の版を、TypeScript 7のAPIで作る

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（docs/review-protocol.mdの未決事項のうち、シンボルIDの表記を決める。ADR-0009の依頼票の項目のうち、`change`と`fixture`の値を広げる）

## 背景

依頼票は固定データで、解析エンジンがなかった（ADR-0002、ADR-0005）。ADR-0010で対象のリポジトリが依頼ごとに決まるようになり、エンジンがどのコードを読むかが決まった。

決める必要があったのは次の点である。

- TypeScriptの解析に何を使うか。inloopはTypeScript 7（Go版）でビルドしている。TypeScript 7には`typescript/unstable/sync`という、型の解決までできるAPIがあるが、名前のとおり不安定とされている。安定したTypeScript 5のAPIを別に入れる手もある。
- シンボルIDの表記（docs/review-protocol.mdの未決事項）。
- 最初の版で、依頼票の何をエンジンで作るか。信頼境界ルールの記述形式、レビュー予算の単位、証拠の取り込みは未決である。

確かめたこと（2026-10-11）: inloop自身のtsconfig.jsonを`typescript/unstable/sync`で読み込むと約0.15秒、関数の中の呼び出し90か所の呼び先を一度に解決して約0.15秒で、呼び先の宣言のファイルと位置が取れた。

## 決定

### 解析の手段

- TypeScript 7の`typescript/unstable/sync`を使う。`typescript`は版を固定して（7.0.2）実行時の依存にする。
- このAPIを使う部分は`src/engine/project.ts`に閉じ込める。APIが変わったとき、別の手段に差し替えるときは、このファイルだけを直す。
- 対象のリポジトリ直下の`tsconfig.json`のプロジェクトを読む。なければ依頼を拒否する。

### シンボルID

- `リポジトリからのパス#名前`とする。区切りは`/`。例: `src/server/target.ts#Targets`。
- クラスのメンバーは`.`でつなぐ。例: `src/server/target.ts#Targets.resolve`。コンストラクターは`constructor`。
- 対象にするのは、ファイルのトップレベルの関数・クラス・インターフェース・型の別名・列挙・変数（`const`など）と、クラスのメソッド・コンストラクター・プロパティ・アクセサー。
- 名前が同じでパスか名前が変われば、別のシンボルとする（名前の変更は追わない）。

### 依頼票の組み立て（最初の版）

- AIが指定したシンボルが1つでも見つからない、シンボルの指定がない、範囲の基点がコミットとして読めない、のどれかなら、依頼票を作らずに拒否し、何も記録しない（ADR-0002のfail-closed）。
- 並べるのは、指定したシンボルと、それが直接使う同じリポジトリのシンボル（呼び出し、`new`、型の参照、継承）。間接の依存はたどらない。
  - クラスを型として参照しただけのときは並べない。`new`したときはコンストラクターを並べる。使うメソッドは、呼び出しから個別に並ぶ。
  - リポジトリの外（`node_modules`、標準ライブラリ）の宣言は並べない。
  - 並べるのは12個までとする。指定したシンボルは必ず入れ、残りを出てきた順の依存で埋める。省いた依存は「未解決の参照」の末尾に、その旨と一覧を示す。
- 順序は、定義が使用より先になるように、依存を先に置く。それ以外はファイルのパスと位置の順。循環があれば、位置の順で先のものから置く。
- コードは作業ツリーのものを、JSDocを含めて示す。
- 変更の印は、範囲の基点（`A..B`ならA、`HEAD`などはその値）と作業ツリーを比べた`git diff`で付ける。基点にないファイルはすべて追加とする。コミットのないリポジトリで基点が`HEAD`なら、すべて追加とする。
- `change`は、シンボルのすべての行が変わっていれば`added`、一部なら`modified`、変わっていなければ`unchanged`（依存として並べたもの）とする。
- 宣言までたどれない呼び出し（`any`の値のメソッドなど）は、推測でつながず「未解決の参照」に`ファイル:行 式`で示す。
- 再依頼でも、そのときのコードで依頼票を作り直す。
- 同じ入力（コード、範囲、指定）からは、同じ依頼票を作る。

### 最初の版で作らないもの

- 信頼境界ルールと必須の依頼。`kind`は常に`optional`、`triggeredBy`と`boundaries`は空。ADR-0001の「信頼境界の変更は必須」は、ルールの記述形式とともに作る。
- レイヤーの判定。`layer`は空にし、UIは空なら表示しない。
- 証拠（テストや静的解析の結果）。`evidence`は空にし、UIは「まだ取り込んでいない」と示す。
- 差分だけの再依頼、承認後の変更の検出。
- レビュー予算の単位。`budget.changedLines`は並べたシンボルの変更行の数、`limit`は仮に40とする。

### 依頼票の値

- `change`に`unchanged`を足す。`fixture`は`true`だけでなく`false`も取る（エンジンが作った依頼票は`false`）。
- 記録の版`v`は上げない（ADR-0009の基準）。すでにある行はそのまま読め、古い実装は新しい行を「依頼票の形が不正」として拒否する。
- 解析エンジンを使わない記録先（`--state-dir`、メモリ、テスト）は、これまでどおり固定データの依頼票を作る。UIの「固定データ」の注意は、`fixture`が`true`のときだけ出す。

## 理由

- TypeScript 7のAPIは、inloopがすでに使っている版で、速く、型の解決までできる。不安定さは、版の固定と、使う部分を1つのファイルに閉じ込めることで抑える。TypeScript 5のAPIを別に入れると、2つの版のTypeScriptを抱え、解析とビルドで型の解釈が食い違いうる。
- シンボルIDは、今の仮の表記を延ばしたもので、AIもリポジトリのパスと名前から書ける。
- 直接の依存だけにするのは、依頼票を人が読み切れる大きさに保つためである。間接の依存は、必要なら別の依頼で指定できる。
- クラスを丸ごと並べると数百行になり、レビュー予算を超える。使うメソッドだけを並べる方が、理解順に沿う。
- 未決のもの（ルール、予算、証拠）を決めたふりをすると、後で覆すことになる（ADR-0009と同じ考え方）。

## 影響

- `typescript`が実行時の依存になった。依頼を作るたびに、TypeScript 7の解析用のプロセスを起動する（1回の依頼で数百ミリ秒）。
- AIは、依頼に実在するシンボルIDを渡す必要がある。渡さなければ拒否される。テンプレートとAIへの指示（`templates/server/AGENTS.md`）の書き方と合う。
- JavaScriptだけのリポジトリ、`tsconfig.json`がリポジトリ直下にないリポジトリ（モノレポなど）は、まだ扱えない。
- SQLは、まだ解析しない（ADR-0005の最初の対象のうち、TypeScriptだけ）。
- `typescript/unstable/sync`の版を上げるときは、エンジンのテストで挙動を確かめる。

## 却下した代替案

- TypeScript 5のAPIを別に入れる: 安定しているが、2つの版を抱える。必要になれば`src/engine/project.ts`を差し替える。
- 構文だけで解析する（型を解決しない）: メソッドの呼び出しの呼び先（`repo.find`）が決まらない。
- 間接の依存までたどる: 依頼票が大きくなりすぎる。
- 型として参照したクラスも丸ごと並べる: 大きすぎる。

## 検証

`npm test`（`test/engine.test.mjs`ほか）で次を確かめる。

- 指定したシンボルと直接の依存を、定義が先の順に並べること
- 型として参照したクラスを並べず、`new`ではコンストラクターを並べること
- 宣言までたどれない呼び出しを未解決として示すこと
- 範囲の基点からの変更を、行と`added`・`modified`・`unchanged`で示すこと。コミットのないリポジトリではすべて追加になること
- 見つからないシンボル、指定のない依頼、読めない範囲、tsconfig.jsonのないリポジトリを、記録せずに拒否すること
- 同じ入力から同じ依頼票を作ること
- 並べる数の上限と、省いた依存の表示
- 再依頼で、そのときのコードから依頼票を作り直すこと
