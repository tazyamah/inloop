# ADR-0043: 端末内で動くアプリに、データの書き出し・読み込みを標準で付ける

- 状態: Accepted
- 日付: 2026-10-13
- Supersedes: なし（ADR-0039、ADR-0041の雛形に足す）

## 背景

端末内で動くアプリ（`--standalone`、`--sync`）のデータは、その端末のブラウザの中（OPFS）にだけある。ブラウザのデータを消す、端末を替える、といったときに失われる。共有しない人には、同期というバックアップもない（ADR-0039の影響、ADR-0041の影響）。

## 決定

- `--standalone`と`--sync`の雛形に、`server/backup.ts`（`GET /api/backup`、`POST /api/backup/import`）と、画面「データ」（`web/src/pages/Backup.tsx`）を入れる。
- 書き出し: データベースの表（`sync_state`を除く）の、列名と行を、JSON（`format: 1`）にする。`sync_state`には、端末の秘密鍵とグループ鍵が入っているので、含めない。スマートフォン（タッチ操作の端末）は、共有メニューから保存し、できなければダウンロードにする。
- 読み込み: 表名・列名は、データベースの中にあるものと照らし、外から来た名前をSQLに使わない。値は、文字列・数・nullだけ。行は合計20万まで。1つのトランザクションで行い、途中で失敗したら元に戻す。
- `uid`と`updated_at`を持つ表（共有する表）は、新しい変更を残して合わせる。読み込んだ行は`dirty = 1`にして、共有先にも送る。それ以外の表は、中身を入れ替える。
- 表を足しても、`backup.ts`は書き換えなくてよい（表と列を、実行時に調べる）。
- 信頼境界ルールの雛形に`backup`を足す。解析エンジンは、`backup.ts`の動的なSQLを「未解決」として扱う。

## 理由

- 実行時に表を調べるので、`inloop generate scaffold`が表を足しても、バックアップの対象に自動で入る。
- 共有する表は、同期と同じ「新しいほうが勝つ」の規則で合わせるので、古いバックアップを読み込んでも、新しい変更を壊さない。

## 影響

- 共有する表で、消した行（`deleted = 1`、手元のほうが新しい）は、古いバックアップを読み込んでも、元に戻らない（新しい消す操作が勝つ）。
- ファイルは暗号化されない。保存場所は、利用者が決める。
- `backup.ts`が、表名・列名を動的にSQLへ入れるので、検証（名前が実在するか）が、レビューの対象になる。

## 却下した代替案

- 表ごとに書き出しの定義を書かせる: 表を足すたびに書き換えが要り、漏れる。
- 書き出しに共有の鍵を含める: ファイルが漏れると、共有に入れてしまう。端末を替えるときは、招待で参加し直す。

## 検証

- 確かめた（2026-10-13、macOS）: 生成した`--standalone`と`--sync`のアプリで、`npm test`（バックアップのテスト4件: 鍵を含まない、読み込みで戻る、新しいほうが勝つ・入れ替え、形の合わないファイルを断って元のまま、APIの書き出し・読み込み）、`npm run build`が通った。Chromiumで、画面から書き出し、まっさらな保存領域に読み込んで、メモが戻ること、この版にない表を含むファイルを断ることを確認した。
- 未検証: iPhoneでの共有メニューからの保存と、ファイルの読み込み。大きなデータ。
