# ADR-0041: 共有は、オーナーの承認と端末ごとの鍵で行い、標準のオプション`--sync`にする

- 状態: Accepted
- 日付: 2026-10-12
- Supersedes: ADR-0040のうち、共有コードによる参加（コードを知っていれば入れる、鍵がコードから決まる）の部分。端末のSQLiteを正とする方針、中継が内容を読めないこと、無料枠で動かすことは変えない

## 背景

ADR-0040の方式は、共有コードを知っている人は誰でも入れ、コードが漏れたときは新しい部屋へ全員が移るしかなかった。利用者は、(1) 承認方式にしたい、(2) 「アプリ入手とは別経路の秘密」だけに頼ると、漏れたときに対処できない、(3) 家族利用ではオーナー（管理者）は1人のはずなので、他のオーナーがいたらアラートを出したい、(4) 無料の利用量を使い切る嫌がらせが心配、(5) 端末間の同期をするPWAを作るときの標準オプションにして、オプション一発で使えるようにしたい、と求めた（2026-10-12）。

## 決定

### 参加者の管理

- 端末ごとに鍵（署名用のECDSA P-256と、鍵の受け渡し用のECDH P-256）を作り、端末のSQLiteに置く。端末の識別子は、署名の公開鍵のハッシュ。
- 共有を始めた端末が**オーナー**（1人だけ）。オーナーが署名した**参加者の記録の鎖**（`root`、`add`、`remove`。番号とひとつ前のハッシュでつなぐ）を、中継と全端末が検証する。
- 参加には、オーナーが作る**招待コード**（部屋の名前16バイト＋秘密10バイト、10分で切れて、1回だけ使える）を、参加する端末が入れる。参加を申し込むと、オーナーの画面に「申し込み」と**確認の数字（4桁）**が出て、参加する端末の画面の数字と見比べて、オーナーが承認する。数字は、両端末の公開鍵と招待の秘密から求める。中継は招待の秘密を知らない（ハッシュだけを預かる）ので、鍵をすり替えると数字が合わない。
- 承認すると、オーナーは、記録（`add`）に署名し、リストの暗号鍵（グループ鍵）を、参加する端末のECDH公開鍵で包んで渡す。中継は、承認された端末だけをつなぐ。
- 参加者を外すと、オーナーは記録（`remove`）に署名し、グループ鍵を新しくして、残る参加者の分を包んで渡す。中継は、行をすべて消し、世代（epoch）を上げる。外された端末は切られ、以後の変更を読めない。残る端末は、新しい鍵で、手元のデータを送り直す。外す前の履歴を、外された端末はすでに持っている。

### 別のオーナーの検出

- 各端末は、受け取った鎖を最初から検証する。オーナー以外の署名、2つ目の`root`、番号やつながりの不整合、すでに持っている記録と同じ番号で内容が違うもの（鎖の分岐）、参加時に確かめたオーナーの鍵と違うものがあれば、**同期を止めて、画面にアラートを出す**。
- オーナーの端末は、自分が作っていない記録が増えていたら（鍵が複製された）、同期を止めてアラートを出す。
- 中継は、検証に通らない鎖の部屋を、参加者なしとして扱う。

### 無料枠を使い切る嫌がらせへの備え

- 接続は、端末の署名つきの証明（`?a=`、2分以内、端末の鍵で署名）が要る。証明のない接続や、許可していないオリジンの接続は、部屋（Durable Object）に入る前にWorkerで断る。
- 部屋の作成は、署名した`root`の記録が要る。作られないまま放置された部屋は1日、使われない部屋は90日で、自動で消す（アラーム）。部屋ごとの上限: 行5000、1行4096文字、参加者20、申し込み20、有効な招待5。1つの接続は、1秒に40メッセージまで、1メッセージ64KBまで。
- 無料枠を超えると、課金されず、中継がエラーを返して共有の同期だけが止まる。アプリは端末で使え、データは失われない。対処は、アプリのREADMEに書く（翌日を待つ、中継を別の名前で置き直す、中継を消す。ドメインを取ればレート制限も使える）。
- 防げないこと: 無料のままでは、Workersの要求数そのものを使い切られることは防げない。

### 標準のオプション

- `inloop new <名前> --sync`は、端末内で動く構成（`--standalone`、ADR-0039）に、共有（`server/sync/`、`relay/`、共有の画面、同期する表の例`notes`）を重ねる。同期する表は、`uid`、`created_at`・`updated_at`、`deleted`、`dirty`の列を持ち、`server/sync-tables.ts`に書く。
- 信頼境界ルールの雛形に、`sync-crypto`、`sync-membership`、`sync-relay`、`sync-config`を足す。層に`sync`と`relay`を足す。
- `inloop generate scaffold`は、`--sync`のアプリには、まだ使えない（同期する表の列が違う）。案内して断る。同期に対応した生成は、あとで足す。

## 理由

- 承認があれば、招待コードが漏れても、数字が合わない・オーナーが承認しない限り入れない。端末ごとの鍵があれば、特定の端末だけを、コードの教え直しなしに外せる。
- オーナーの署名の鎖を全端末が検証するので、中継が侵害されても、偽の参加者を足せない。中継の改ざんは、アラートで分かる。
- 中継を内容の読めない受け渡しに限ると、運用者に見えるのは、行の識別子と更新時刻と大きさだけになる。

## 影響

- オーナーの端末をなくすと、承認と外す操作ができなくなる。共有を作り直す必要がある（共同オーナーと復旧は、まだない）。
- 承認には、オーナーの端末がオンラインである必要がある。
- 端末の秘密鍵とグループ鍵は、端末のSQLiteに、そのまま入っている（その端末にアクセスできる人は読める）。
- 同じ行を同時に変えたときは、更新時刻（端末の時計）が新しいほうが勝つ。
- 中継の変更で、ADR-0040の中継とは互換がない（買い物リストは、新しい雛形へ移し直す）。
- 古い世代の行は、鍵の更新で全部消える。残る端末が送り直すので、そのとき、全員がオンラインでなくても、次につながったときに戻る。

## 却下した代替案

- 招待コードの代わりに、別経路のパスコードを足す: 漏れたときに対処できず、共有コードと同じ種類の秘密が増えるだけ。
- Cloudflare Accessでメールの許可リスト: アプリを開く画面の制限にはなるが、PWAのオフライン動作と相性が悪く、内容の暗号化の代わりにならない。
- 共同オーナーを最初から入れる: 暗号と手順が増える。まず1人のオーナーで作り、必要になったら足す。

## 検証

確かめた（2026-10-12、macOS）:

- 生成したアプリで`npm test`が17 pass（暗号、鎖の検証と不正の検出、中継の認可・上限、オーナー1人と参加者2人の同期、オフライン中の変更の送信、同時変更の解決、参加者の取り外しと鍵の更新、オーナー鍵の複製・偽のオーナーの記録でのアラート、断られた参加、同期のURLがないとき）。
- ローカルの中継（`wrangler dev`、Cloudflare Workersの実行環境）と、2つのブラウザ（別の保存領域のChromium）で、画面から、共有を始める、招待コードを作る、参加を申し込む、確認の数字が同じことを見る、承認する、メモが届く、参加者を外す、外された端末にアラートが出る、まで通った。

- 本物のCloudflare（中継は`workers.dev`、画面は`pages.dev`）に置いた買い物リスト（`inloop new --sync`で作成）で、同じ流れ（共有を始める、招待、確認の数字が同じ、承認、品物が届く、外す、外された端末のアラート）を、2つのブラウザで確認した。許可していないオリジンは403、証明のない接続は401。

- iPhone実機（2台）で、承認の流れ（招待、確認の数字、承認）が動いたと、利用者が確認した（2026-10-13、利用者の発言）。

未検証:回線の切断からの再接続（実ブラウザ）。休止（ハイバネーション）からの復帰。オーナー鍵の複製のアラートを、実ブラウザで見ること。無料枠の使い切りの挙動。
