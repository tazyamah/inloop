# ADR-0008: 1回の呼び出しで出された依頼を、回答のまとまりにする

- 状態: Accepted
- 日付: 2026-10-10
- Supersedes: なし

## 背景

サーバーは、どの依頼がどの会話のものかを知らず、受付箱が全会話で1つだった。そのため、会話1に表示されたUIから、会話2で出された依頼に回答できた。そうすると、回答のメッセージは会話1に入り（UIからの`sendMessage`は、UIが表示されている会話に届く）、依頼した会話2のAIは再開せず、依頼は回答済みになって正しい会話から答え直せない。依頼と回答を保存するようにして（ADR-0007）再起動後も残るようになり、利用者の指摘で表面化した。

会話を区別する手段を、Claude Desktop（2026-10-10、クライアント名`claude-ai` 0.1.0）で調べた。

- ホストが渡す情報: 2つの会話からの依頼は同じ1つのサーバープロセスに届き（`initialize`は1回）、AIからの`tools/call`の`_meta`は`null`、UIからの呼び出しは`progressToken`だけだった。会話を区別できる情報はない。
- AIに印を持ち回らせる方式: サーバーが発行した印を`request_review`の戻り値で返し、同じ会話の次の依頼で引数に渡させた。同じ会話で続けて2件依頼する試行を4回行い、すべてで2件目に印が渡されなかった。試したのは、(1) 任意の引数と説明文、(2) 説明文で必須と強調、(3) 必須の引数にして最初だけ`"new"`を渡させる、(4) さらに戻り値に「以後の依頼でこの印を渡すこと」と添える、の4通りである。AIは戻り値の印を読めていた（返答の中で印に言及した）が、渡さなかった。

つまり、会話をまたいで依頼を束ねる確実な手段はなかった。

## 決定

- 1回の`request_review`の呼び出しで、複数の依頼を出せるようにする。引数は`reviews`（観点とシンボルIDの組を1〜10件）と、共通の`range`とする。
- 1回の呼び出しで作った依頼を「まとまり」とし、1つのUIの受付箱に並べ、まとめて1通で回答できるようにする。
- 別の呼び出しで作った依頼を、同じまとまりにする手段は設けない。同じ会話であっても、別の呼び出しの依頼は別のUIから回答する。
- まとまりは、その呼び出しで最初に作った依頼のIDで表し、依頼票の`group`に記録する。AIには返さない。
- 戻り値は依頼IDと状態だけとする（テキストは`R1 R2 pending`、structuredContentは`{ids}`）。
- UIは、開かれた依頼と同じまとまりの依頼だけを受付箱と宛先候補に出す。ほかの未回答の依頼は、件数だけを知らせる。
- `inloop_submit`は、UIが開かれた依頼のID（`from`）を必須とし、`from`とまとまりが異なる依頼への回答が1つでもあれば全体を拒否する。UIの表示だけに頼らず、サーバーで強制する。
- `get_review_result`は`ids`を必須とする。絞り込みなしでは返さない。
- 1回の呼び出しの依頼は、1回の書き込みで記録する。
- `group`のない古い記録の依頼は、その依頼だけのまとまりとして扱う。記録の版`v`は上げない。

## 理由

- 1回のツール呼び出しは、必ず1つの会話の中で起きる。その結果を表示するUIも同じ会話にある。呼び出しをまとまりの単位にすれば、ホストの情報にもAIの記憶にも頼らずに、会話をまたがないことを仕組みとして保証できる。
- AIが機能を作り終えて、複数の観点をまとめて聞く使い方（ADR-0001）と合う。呼び出しが1回で済むので、AIの文脈も減る。
- まとまりをAIに見せないので、AIが誤った値を渡して別の依頼に紛れ込む経路がない。

## 影響

- 時間をおいて別々に出された依頼は、同じ会話でも、まとめて回答できない。それぞれのUIから回答する。AIが観点を1回にまとめて出すかどうかが、使い勝手を左右する。スキルやツールの説明文で促す。
- `request_review`の引数の形が変わった（`viewpoint`と`symbols`を直接渡す形から、`reviews`の配列へ）。戻り値は、1件なら以前と同じ`R1 pending`である。
- AIから見えるツール定義2件は838文字から1043文字になった。
- 修正後の再依頼（差分の再レビュー）は新しい呼び出しになるので、元の依頼とは別のまとまりになる。再依頼の仕組みを作るときに、元の依頼との対応づけを別に決める。
- ブラウザで開く代替経路（未実装）は会話の中に表示されないので、どの依頼を見せるかを別に決める必要がある。

## 却下した代替案

- ホストが渡す情報で会話を区別する: Claude Desktopは渡していなかった。
- サーバーが発行した印をAIに持ち回らせる: 背景のとおり、4通り試してAIは一度も渡さなかった。戻り値も長くなる。
- UIは自分が開かれた依頼1件にだけ回答できるようにする: 複数の依頼をまとめて1通で回答できなくなる（ADR-0004）。
- サーバープロセスや接続ごとに分ける: Claude Desktopは複数の会話で1つのプロセスを共有していた。
- 受付箱は共有したまま、ほかの依頼を回答不可として一覧に出す: 別の会話の問いの文面まで見せる必要が薄く、取り違えの余地が残る。件数だけにした。

## 検証

`npm test`で次を確認する。

- 1回の呼び出しの依頼が同じ受付箱に入り、別の呼び出しの依頼は入らないこと
- 別の呼び出しの依頼への回答を含む送信を、全体として拒否し、何も記録しないこと
- `get_review_result`が、IDなしでは返さず、指定したIDの分だけを返すこと
- 1回の呼び出しの依頼が連続した行として記録され、再起動後もまとまりが変わらないこと
- `group`のない古い記録の依頼が、その依頼だけのまとまりになること

`INLOOP_UI_E2E=1 npm test`で、別の呼び出しの依頼が受付箱と宛先候補に出ず、件数だけが表示されることを確認する。

実際のクライアントで、AIが複数の観点を1回の呼び出しにまとめるか、まとめた依頼が1つのUIに並ぶかは未検証である。
