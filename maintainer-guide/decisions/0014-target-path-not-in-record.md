# ADR-0014: 対象のリポジトリのパスは記録に書かず、記録の置き場所で表す

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: ADR-0010の一部（「依頼票に対象（`repo`）を記録する。UIは依頼票の上部に対象を表示する。」と、`--state-dir`を指定した場合の対象の決め方）

## 背景

ADR-0010を実装するときに、依頼票に対象のリポジトリの絶対パスを書くと、リポジトリを移したり複製したりしたときに、記録の中のパスが実際の場所と食い違うことに気づいた。記録（`<リポジトリ>/.inloop/reviews.jsonl`）はリポジトリと一緒に動くので、記録の置き場所そのものが対象を表している。利用者は、遠い未来に記録を参照したときに矛盾がないことを優先している。

また、ADR-0010は`--state-dir`を「記録先だけを上書きする互換の手段」としたが、対象が決まらないときの扱いを書いていなかった。いまのClaude Desktopの登録は`--state-dir`を使っており、AIは`repo`を渡さない。

## 決定

- 依頼票と記録の行に、対象のリポジトリのパスを書かない。対象は、記録ファイルの置き場所で表す。依頼票の形は変えない（ADR-0009）。
- 対象のパスは、実行中だけ使う。MCP Appsでは、`request_review`の結果の`_meta`（`inloop/repo`）でUIに渡し、UIはUI専用のツールにそのまま渡す。AIに渡る`structuredContent`には入れない。ブラウザで開く経路では、URLに対象の短い印（パスのハッシュの先頭10文字）を入れ、サーバーがプロセスの中で印とパスを対応づける。画面が渡した`repo`は使わない。
- UIに対象を表示することは、この判断では行わない。ADR-0013を実装するとき、URLのアプリ名で示す。
- `--state-dir`（または`INLOOP_STATE_DIR`）を指定した場合は、すべての依頼をそこに記録する。対象が決まらなくても拒否しない（これまでの登録との互換）。対象が決まった場合も、gitの作業ツリーであることなどの確認は行い、記録先だけを`--state-dir`にする。
- `--state-dir`がなく、対象も決まらなければ、ADR-0010のとおり拒否する。これまでの「指定がなければメモリにだけ保持する」動きはなくなる。

## 理由

- 記録の置き場所で対象を表せば、リポジトリを移しても記録の中に古いパスが残らない。
- 対象のパスをAIの文脈に入れない（ADR-0004、ADR-0010）。
- いまのClaude Desktopの登録を、作り直さずに動かし続けるため、`--state-dir`では対象を求めない。

## 影響

- 1つの`--state-dir`に複数のリポジトリの依頼を記録すると、記録からはどのリポジトリの依頼か分からない。`--state-dir`は、対象が1つの場合の互換の手段と位置づける。
- MCP AppsのUIが対象を知るのは`_meta`だけになる。ホストが`_meta`をUIに渡さない場合、UIは対象を渡せず、`--repo`もrootsも`--state-dir`もなければ、UIの操作は拒否される。Claude Desktopが`_meta`を渡すかは未検証。
- ブラウザで開く経路のURLは`/r/<対象の印>/<依頼ID>`になった。ADR-0013を実装するとき、アプリ名のURLに置き換える。

## 却下した代替案

- 依頼票に絶対パスを書く（ADR-0010のとおり）: 背景のとおり、移動や複製で食い違う。
- 依頼票にリポジトリ内の識別子（リモートのURLなど）を書く: リモートのないリポジトリがあり、複製でも同じ値になるので、対象を区別できない。

## 検証

`npm test`で次を確かめる。

- 記録の行に対象のパスが入らないこと（依頼票の形は変わらない）
- `request_review`の結果の`_meta`に対象が入り、`structuredContent`には入らないこと
- ブラウザで開く経路で、このプロセスが作っていない対象の印を拒否すること
- `--state-dir`を指定すると、対象が決まらなくても記録すること
