# ADR-0017: 議論は会話で行い、画面は読む場所と記録にする。依頼の大きさに上限を設ける

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（ADR-0009の「承認は人の回答だけが起こす」を、会話での人の指示による記録に広げる。ADR-0004のAIから見えるツールを1つ足す）

## 背景

Claudeデスクトップアプリの中のClaude Codeで、ブラウザペインの画面を横に開いて使うようになって、利用者から次の指摘があった（2026-10-11）。

- 画面の「回答」欄で質問しても、答えはその画面ではなく会話に来る。横に開いたブラウザでは、会話でやりとりしたほうが早い。埋め込みの画面（Claude Desktopの通常の会話）では、その場で答えてよい気がしていた。
- 画面は、記録として見るには見やすい。実際の作業では、画面からコードの位置をコピーして会話で「ここの範囲なんだけど」と話し、承認や保留の結果をAIがまとめる形がよいのではないか。
- 依頼票はR6（5シンボル、54行）くらいが一度に認識できる限界に感じる。行数で感じている。個人差があるので設定で変えたい。表示の側では省かず、AIの側に制限を課すほうがよい（R4の指摘）。
- 承認・保留は、会話で決まった言葉（「承認」「保留」、設定で変えられ、「開けゴマ」でもよい）を言われたらAIが記録する。それを唯一の経路にはせず、画面のボタンでもよい。

## 決定

### 利用者ごとの設定

- 利用者ごとの設定ファイルを`~/.inloop/config.json`（`INLOOP_HOME`で変えられる）とする。リポジトリには置かない（感じ方の個人差のため）。読むたびにファイルから取り直す。項目は次の3つ。
  - `maxReviewLines`（既定60）: 依頼票に並べるコードの行数の上限。
  - `approvePhrase`（既定「承認」）・`holdPhrase`（既定「保留」）: 会話でAIに承認・保留を記録させる言葉。同じ言葉にはできない。

### 依頼の大きさの上限

- 依頼票に並べるコードの行数の合計が`maxReviewLines`を超え、対象のシンボルが2つ以上なら、依頼を断り、シンボルを分けて別々の依頼にするようAIに返す。何も記録しない。
- 対象のシンボルが1つなら、それ以上小さくできないので、行数にかかわらず受け付ける。
- 依存として並べたシンボルの行も数える（人が読む量だから）。

### 位置のコピー

- 画面の各シンボルの見出しとコメント欄に「位置をコピー」を置く。回答できる依頼のない行は、クリックで位置をコピーする（Shiftで範囲）。
- 位置の文字列は、回答の1行と同じ形の`<依頼ID> <参照>`とする。例: `R6 src/server/wait.ts#answersOf#L12-L15`。
- クリップボードが使えなければ、選択してのコピーを試し、それもできなければ文字列を示す。

### 会話での承認・保留の記録

- AIから見えるツール`answer_review`（`ids`、`verdict`は`ok`か`hold`、`said`、省略できる`repo`）を足す。AIは、人が会話で設定の言葉をはっきり言ったときだけ呼ぶ。`said`には人が言った言葉をそのまま渡す。
- サーバーは`said`が設定の言葉と一致するときだけ記録する。一致しなければ記録しない。
- 会話から記録できるのは承認・保留だけで、修正依頼と質問は会話のやりとりそのものとする。必須（`required`）の依頼は、会話からは記録できず、画面で人が答える（ADR-0001）。
- 記録は新しい種類の行`chatAnswer`とする。古い実装は知らない種類として拒否するので、人の回答と読み違えない（ADR-0009の基準により、版は上げない）。
- 画面では「承認済み（会話で）」「回答済み（保留）・会話で」のように区別して示し、回答の履歴に「会話での指示をAIが記録」と添える。
- 画面の承認・保留のボタンはそのまま使える。会話から記録した保留も、画面で未回答に戻して答え直せる。

## 理由

- 横に開いた画面では、会話が議論の場として自然である。画面は、何を見せて何が決まったかの記録として残す（遠い未来に参照したときの矛盾を避ける、という利用者の方針と合う）。
- 言葉の照合は、AIが会話の流れを推し量って承認してしまう取り違えを防ぐ。ただしAIはこのMacの設定ファイルも読めるので、強制ではなく取り違えの防止である。AIは記録ファイルを直接書けるという前提（ADR-0012、ADR-0013）は変わらない。
- 必須の依頼を会話から承認できないようにするのは、「信頼境界の依頼をAIの判断で省ける経路を作らない」（ADR-0001、AGENTS.md）を守るためである。
- 行数の上限を1シンボルの依頼に課さないのは、既存の大きな関数を対象にした依頼が、ずっと断られ続けるのを避けるためである。

## 影響

- AIから見えるツールが3つになり、ツール定義は約1800文字になった（テストの上限を1500から2000にした）。
- 1つの依頼で多くのシンボルを指定すると断られるようになる。AIは小さな単位で依頼を出す必要がある。
- 行数の上限は、データの流れなどの図で人が判断できるようになれば、不要になるかもしれない（利用者、2026-10-11）。
- 修正依頼と質問のやりとりは、会話にだけ残り、記録には残らない（これまでと同じ）。

## 却下した代替案

- AIが議論の要点を下書きし、人が画面で確定する（相談時の案A）: 確定のたびに画面を操作する必要がある。利用者は会話の言葉で記録できるほうを選んだ。
- AIが会話の結論を見て、言葉なしに承認・保留を記録する（案B）: 取り違えを防げない。
- 表示する数に上限を設ける: R4の指摘のとおり、省いた部分が見えなくなる。

## 検証

`npm test`で次を確かめる。

- 行数の上限を超えた2つ以上のシンボルの依頼を断り、1つのシンボルなら受け付けること。上限を設定で変えられ、不正な設定を示すこと
- `answer_review`が、設定の言葉と一致するときだけ記録し、言葉を設定で変えられること。記録の種類が`chatAnswer`で、画面に「会話で」が渡ること
- 必須の依頼、回答済みの依頼を会話から記録できないこと。会話から記録した保留を、画面で未回答に戻して答え直せること

`INLOOP_UI_E2E=1 npm test`で、位置のコピー（見出し、コメント欄、回答済みの行）を確かめる。
