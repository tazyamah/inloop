# ADR-0009: 再依頼を枝番のIDで表し、保留と質問は同じ依頼のまま未回答に戻す

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（ADR-0007の「行の種類は2つ」と「依頼IDの振り方」、ADR-0008の「まとまりの値」を広げる。どちらの結論も変えない）

## 背景

依頼は回答されると`fixing`・`answering`・`held`・`approved`のいずれかになり、そこから動かせなかった。[review-protocol](../../docs/review-protocol.md)の草案は、この3つが`pending`に戻ると書いていたが、戻し方は決めていなかった。決める必要があったのは次の点である。

- 修正後の再依頼を、元の依頼とどう対応づけるか（ADR-0008が持ち越した）。再依頼は新しい呼び出しなので、元の依頼とは別のまとまりになる。
- 保留と質問を、誰がどう未回答に戻すか。
- 依頼票の構造を変えるか。変えるなら、記録の版`v`を上げるか（ADR-0007が持ち越した）。

再依頼には2つの案があった。同じIDのまま未回答に戻す案は、IDが変わらない利点があるが、1つのIDが複数の依頼票と複数のまとまりを持つことになる。さらに、再依頼の画面と元の画面が同じIDを名乗るため、別の会話から再依頼されると、元の会話の画面から回答できてしまう（ADR-0008が塞いだ問題）。画面を区別するには、呼び出しごとの印をツールの結果で画面に渡す必要があり、AIに見せずに渡せるかはホスト次第だった。

## 決定

### 依頼ID

- 新しい依頼のIDは`R13`の形とする。その再依頼は、枝番を付けた`R13-1`、次は`R13-2`とする。枝番は1から順に振り、重ねない（`R13-1-1`は作らない）。
- 枝番を除いたIDが同じ依頼を「系列」と呼ぶ。系列の中で枝番が最も大きい依頼が、最新の依頼である。
- 1つのIDは、1回の呼び出しで人に見せた1つの依頼票を指す。依頼票もまとまりも、作った後は変わらない。
- 新しい依頼の番号は、枝番に関係なく、記録にある最大の番号の続きから振る。

### 状態と遷移

状態は`pending`・`approved`・`fixing`・`answering`・`held`・`superseded`の6つとする。`superseded`（再依頼済み）は、枝番の依頼に引き継がれ、もう回答できない状態である。

| 遷移 | 起こすもの | IDと依頼票 |
|---|---|---|
| `pending` → `approved`・`fixing`・`answering`・`held` | 人の回答 | 変わらない |
| `held`・`answering` → `pending` | 人が、その依頼の画面で未回答に戻す | 変わらない |
| `superseded`以外 → `superseded`、同時に枝番の依頼が`pending`で始まる | AIの再依頼 | 新しいIDと新しい依頼票 |

- `fixing`と`approved`は、人の操作では未回答に戻せない。依頼票が修正前のものなので、戻して承認すると、見ていないコードを承認することになる。再依頼で引き継ぐ。
- 再依頼は、`superseded`を除くどの状態の依頼にも出せる。未回答のまま出し直すことも、承認済みの依頼をもう一度見てもらうこともできる。どの場合も、それまでの最新の依頼は`superseded`になる。
- 再依頼によって依頼が承認されることはない。承認は人の回答だけが起こす。
- マージの条件（ADR-0001）は、`superseded`を除くすべての依頼が`approved`であること、と読み替える。系列は、最新の依頼の状態で判定される。

### AIとのやり取り

- `request_review`の`reviews`の各項目に`follows`（元の依頼のID）を渡すと、再依頼になる。戻り値は、これまでと同じくIDと状態だけである（`R13-1 pending`）。
- `follows`には、系列のどのIDを渡してもよい。引き継ぐのは、常に最新の依頼である。
- `follows`があれば`viewpoint`と`symbols`は省略でき、省略したものは最新の依頼から引き継ぐ。`follows`のない項目は`viewpoint`が必須である。
- 1回の呼び出しに、新しい依頼と再依頼を混ぜてよい。同じ系列への再依頼を2つ含む呼び出し、存在しないIDを`follows`に持つ呼び出しは、全体を拒否し、何も記録しない。
- 再依頼も、その呼び出しのまとまりに入る（ADR-0008）。まとまりの値は、その呼び出しで最初に作った依頼のIDで、枝番のIDのこともある。
- 回答のメッセージの先頭行で、`fix`は修正後に`follows`で再依頼すること、`ask`は会話で答えることをAIに伝える。
- 未回答に戻したことは、AIに伝えない。戻した依頼に回答した時点で、その回答が届く。

### UI専用のツール

- `inloop_reopen`（`visibility: ["app"]`）を足す。引数は`from`（画面が開かれた依頼のID）と`ids`。`from`とまとまりが異なる依頼、`held`・`answering`以外の依頼が1つでもあれば、全体を拒否する。
- `inloop_get_request`の戻り値に`history`を足す。その依頼と、同じ系列でそれより前の依頼に、これまで記録された回答である。再依頼の画面で、前回の指摘を見せるために使う。AIには返さない。
- 受付箱の各項目に、再依頼済みの場合の引き継ぎ先`supersededBy`を足す。

### 記録

- 行の種類を1つ足す。`reopen`は、未回答に戻した依頼のIDの列`ids`を持つ。1回の操作を1行にまとめる。
- 再依頼は、枝番のIDを持つ`request`として記録する。元の依頼への参照は別に持たず、IDから決める。
- 読み込みでは、次を拒否する。存在しない系列への再依頼、枝番が最新の次でない再依頼、`superseded`の依頼への回答、`held`・`answering`以外の依頼を戻す`reopen`、IDが重複した`reopen`。
- `get_review_result`が返すのは、依頼ごとに、現在の状態を決めた回答だけである。未回答に戻した依頼の、戻す前の回答は返さない。

### 依頼票の構造と、記録の版

- 依頼票の構造は、現在の形のまま確定する。項目は[review-protocol](../../docs/review-protocol.md)の「依頼票の項目」のとおりで、`src/server/types.ts`の`ReviewPacket`が対応する。変えたのは、`id`と`group`が枝番のIDを取りうることだけである。
- 読み込みで、依頼票の形の全体を確かめる。これまでは`id`・`viewpoint`・`steps`の有無だけだった。形が合わない依頼票は、合わない場所を示して拒否する。知らない項目は無視し、UIにも渡さない。
- 記録の版`v`は1のまま上げない。
- 版を上げるのは、次のどちらかに当たるときとする。
  - すでにある行を、そのままでは読めなくなる。
  - 古い実装が、新しい行を拒否せずに、別の意味で読んでしまう。
- 版を上げるときは、新しい行だけを新しい版で書き、読む側は対応するすべての版を読む。追記専用なので、古い行は書き換えない。
- 次は、この判断では決めない。解析エンジンを作るときに決め、依頼票の形が変わるなら上の基準で版を判断する。
  - シンボルIDの表記と、revision間で同一性を保つ方法
  - レビュー予算の単位
  - 信頼境界ルールの記述形式と、`required`の依頼の再依頼で種別と根拠のルールを決め直す方法
  - 承認後に対象シンボルの本文が変わったことの検出（草案の「承認後に変わったら`pending`に戻る」）。検出したときは、この判断の再依頼と同じく、系列の新しい依頼として表す。

## 理由

- 枝番のIDは、再依頼のたびに新しいIDになるので、IDごとに依頼票が1つ、呼び出しが1つ、まとまりが1つ、という前提（ADR-0007、ADR-0008）が残る。画面は自分のIDだけで自分の呼び出しを特定でき、ホストに頼らない。別の会話から再依頼されても、元の画面から回答する経路はサーバーが塞ぐ。
- 枝番は元のIDを含むので、AIも人も、どの依頼の続きかを追加の情報なしで読める。元の依頼への参照を別に持つと、IDと食い違いうる。
- 保留と質問では、見せるコードが変わらない。同じ依頼票のまま、同じ画面で回答し直せば足りる。AIの呼び出しが要らないので、AIの文脈を使わない（ADR-0004）。
- 修正待ちを人が戻せないようにするのは、「何を見て承認したか」を記録と一致させるためである（ADR-0007）。
- `follows`に系列のどのIDでも渡せるようにするのは、AIの文脈に古いIDが残るからである。系列は1つに決まるので、推測にはならない。
- 版を上げないのは、基準のどちらにも当たらないからである。
  - すでにある行は、そのまま読める。依頼票の項目は増えても減ってもいない。これまでの依頼票はすべて固定データから作られ、その形は最初の実装から、まとまり（`group`）が増えただけである。
  - 古い実装は、新しい行を必ず拒否する。枝番のIDは古い実装の依頼IDの形に合わず（`依頼票の形が不正`）、`reopen`は知らない種類である。枝番の依頼への回答や、戻した依頼への回答が現れるのは、その後である。古い実装が新しい記録を読んで、再依頼済みの依頼を修正待ちのまま見せる、といった読み違いは起きない。1つ前のcommitの実装に新しい記録を読ませて、この2つの拒否を確かめた（2026-10-11）。
- 依頼票の残りの項目（シンボルIDの表記など）を今決めないのは、解析エンジンがないと確かめられないからである。決めたふりをすると、エンジンを作るときに覆すことになる。

## 影響

- `request_review`の`reviews`の項目に`follows`が増え、`viewpoint`は`follows`があれば省略できるようになった。AIから見えるツール定義2件は1043文字から1139文字になった。
- 回答のメッセージの先頭行が46文字から62文字になった。
- 状態に`superseded`が増えた。UIは「再依頼済み → R13-1」と表示する。
- 依頼IDに`-`が入る。回答の1行の形式（`R13-1 fix src/auth.ts#login#L42 "..."`）は変わらない。
- 元の画面のまとまりには、再依頼済みの依頼が残る。再依頼は別のまとまりなので、元の画面からは回答できない。
- 新しい版のサーバーが`reopen`か枝番の依頼を書くと、同じ記録を使っている古い版のサーバーは、その行で止まる。再起動して新しい版にすれば読める。
- 形の合わない依頼票が記録にあると、サーバーは起動しない。これまでは、UIが表示に失敗するまで分からなかった。
- 再依頼の依頼票は、いまは固定データなので、元の依頼と同じ内容である。差分だけを見せる仕組み（ADR-0004）は、解析エンジンと合わせて作る。そのとき、承認時のシンボル本文との比較には、系列の記録を使える。
- `required`の依頼の再依頼は、いまは固定データがすべて`required`なので、種別が変わらない。解析エンジンを作るとき、AIが再依頼で`required`を外せないことを、サーバーで保証する必要がある（ADR-0001）。

## 却下した代替案

- 同じIDのまま未回答に戻す: 背景のとおり、1つのIDが複数の依頼票とまとまりを持ち、画面を区別する印をホスト経由で渡す必要がある。
- 新しい通し番号を振り、元の依頼への参照を項目として持つ（`R20`が`R13`を引き継ぐ）: 前提は保てるが、IDから続きだと読めない。参照の項目を古い実装が無視して読み違えるので、版を上げる必要があった。
- 枝番を重ねる（`R13-1-1`）: 系列は一本道なので、深さに意味がない。IDが長くなる。
- 質問も、AIの再依頼で戻す: コードが変わっていないのに、呼び出しと新しいIDが増える。AIがコードを変えたときは、再依頼すればよい。
- 保留中の依頼に、未回答に戻さず直接回答できるようにする: 記録の種類は増えないが、「回答できるのは未回答の依頼だけ」という読み込みの規則が崩れる。
- 人が修正待ちや承認済みの依頼も未回答に戻せるようにする: 修正前の依頼票のまま承認できてしまう。承認の取り消しは必要になったら別に決める。
- 版を2に上げ、知らない項目のある行を拒否する: 厳密だが、今回の変更は基準に当たらない。利用者の記録にある、捨てた方式の項目（`thread`）を読めなくなる。

## 検証

`npm test`で次を確認する。

- 再依頼が枝番のIDになり、元の依頼が再依頼済みになること。観点と対象を引き継ぐこと。新しい呼び出しのまとまりに入ること
- 系列のどのIDを渡しても最新の依頼を引き継ぐこと。新しい依頼の番号が枝番に関係なく続くこと
- 再依頼済みの依頼に、どの画面からも回答できないこと
- 不正な再依頼を含む呼び出しを全体として拒否し、何も記録しないこと
- 保留中・回答待ちの依頼だけを、同じまとまりの画面から未回答に戻せること。戻した後に回答し直せること
- 再依頼と`reopen`の記録から、再起動後も同じ状態・履歴・次のIDが再現されること
- 状態遷移に合わない記録を、行を示して拒否すること
- 依頼票の形の全体を読み込みで確かめ、知らない項目を無視すること
- 記録の版が1のままであること

`INLOOP_UI_E2E=1 npm test`で、未回答に戻す操作、これまでの回答の表示、再依頼済みの表示、再依頼の画面から枝番のIDで回答できることを確認する。

実際のクライアントで、AIが修正後に`follows`を付けて再依頼するか、質問に会話で答えるかは未検証である。
