# ADR-0030: SQLを実行する宣言を、呼び出しを2段までたどって探す

- 状態: Accepted
- 日付: 2026-10-12
- Supersedes: なし（ADR-0026の「間接は対象にしない」、ADR-0028の「2段以上の間接は作らない」を、ここで足す）

## 背景

ADR-0026の`tables`は、依頼票に並べた宣言の中の`prepare`・`exec`だけを読む。ルートの処理が`createNote(db)`のようなデータ層の関数を呼ぶ形だと、依頼票の対象は並べた直接の依存までなので、その先のSQLが見えない。ADR-0028の`table`の当て方も、対象と、それが直接使う宣言までしか調べなかった。標準の構成（ルート→関数→データ層）では、実際の書き込みが2段以上先にあることが多い。

## 決定

- SQLを探す範囲を、呼び出し・`new`でたどれる同じリポジトリの宣言へ、2段（`INDIRECT_DEPTH`）まで広げる。型の参照・継承はたどらない（SQLを実行しないため）。
- 依頼票の`tables`:
  - 項目に省略できる`via`（シンボルIDの列）を足す。`symbol`の次の呼び出し先から、SQLを持つ宣言までを並べる。直接のSQLには付けない。記録の版は1のまま。
  - 起点は、依頼票に並べた各宣言。並べた宣言は、自分の分を自分の`symbol`で持つので、そこでたどるのを止める（二重に出さない）。
  - たどった宣言の動的なSQLと未解決の参照は、依頼票の`unresolved`に足す（その先にSQLがあるか分からないため）。
  - 画面は`（a → b 経由）`を付けて出す。
- `table`の当て方: 対象のコードが直接使う宣言から、さらに2段先までのSQLにも当てる（合計で対象から3段）。動的なSQLの扱いはADR-0028のまま。

## 理由

- 標準の構成で、書き込みの信頼境界に触れる変更が、関数を1つ挟んだだけで見えなくなるのを防ぐ（AGENTS.md: 信頼境界ルールの省略経路を作らない）。
- 深さの上限があるので、解析は有限で、依頼票の大きさも抑えられる。上限の先は見えないが、`via`で「どこまでたどったか」が分かる。

## 影響

- 既存の記録は`via`なしのまま読める。古い実装は`via`のある記録を、知らない項目として無視する。
- `table`のルールを持つリポジトリでは、`request_review`のたびに、呼び出し先を2段ずつたどって読む量が増える。大きなリポジトリでの時間は未確認。
- 動的dispatch、コールバックとして渡した関数、別のファイルから再exportした名前は、たどれない（呼び出しとして解決できなければ、未解決として出る）。

## 却下した代替案

- 無制限にたどる: 依頼票とルールの当たる範囲が、共通のユーティリティ経由で全体に広がる。
- 並べた宣言も通り抜けて重ねて出す: 同じSQLが複数の行に出て、人が数えにくい。

## 検証

`npm test`で、並べた宣言の先のSQLが`via`つきで出ること、並べた宣言で止まること、深さの上限、`table`のルールが2段先のSQLに当たることを確かめる。実際のクライアントでの表示は未検証。
