# ADR-0010: 対象のリポジトリを依頼ごとに決め、記録をリポジトリごとに置く

- 状態: Accepted
- 日付: 2026-10-11
- Supersedes: なし（ADR-0007の「状態ディレクトリは起動時に指定する」を、対象のリポジトリから決める形に広げる）

## 背景

inloopで複数のアプリ（アプリa、アプリb）を作るときの、ファイルの置き方が決まっていなかった。

- ADR-0007は、記録を対象のリポジトリ直下の`.inloop/`に置くことを推奨しているが、記録先は起動時の`--state-dir`で1つに決まる。クライアントへの登録は普通1つなので、アプリaとアプリbの記録が同じファイルに混ざる。分けるには、アプリごとに登録を作る必要がある。
- 解析エンジンが読む対象のリポジトリの場所も、未決だった（handoffの次の一手2番）。依頼票が固定データなので、まだ問題になっていなかった。
- サーバーは、どの依頼がどの会話のものかを知らない。Claude Desktopは複数の会話で1つのサーバープロセスを共有し、AIからの呼び出しの`_meta`は`null`だった（ADR-0008）。つまり、プロセスや接続の単位でリポジトリを1つに決めることは、Claude Desktopではできない。
- AIは、サーバーが発行した印を次の呼び出しへ持ち回らなかった（ADR-0008）。一方、リポジトリのパスは、AIがそこで作業している以上、AI自身が知っている値である。
- MCPには、クライアントが作業フォルダをサーバーに知らせる仕組み（roots）がある。Claude DesktopとClaude Codeが対応しているかは、確かめていない。

この判断では、現在のクライアントの制約に合わせる前に、inloopとして正しい形を決める。制約で変える部分は、決定の中で分けて書く。

## 決定

### 対象とその表し方

- レビューの対象は、gitの作業ツリー1つとする。表し方は、作業ツリーの最上位の絶対パス（`git rev-parse --show-toplevel`の結果）とする。シンボルIDとファイルの参照は、そこからの相対パスで書く。
- 依頼ID、まとまり、系列、記録、依頼票の生成は、すべて対象ごとに独立する。アプリaの`R1`とアプリbの`R1`は別の依頼である。

### 記録の置き場所

- 記録は`<対象>/.inloop/reviews.jsonl`に置く。形式はADR-0007のまま。
- サーバーは`.inloop/`を作るとき、中に`*`だけを書いた`.gitignore`を置く。対象のリポジトリの`.gitignore`は変えない。
- 起動時の`--repo <dir>`で、そのプロセスの対象を1つに固定できる。リポジトリごとに登録するクライアント（Claude Codeの`.mcp.json`、ADR-0011）で使う。
- `--state-dir`と`INLOOP_STATE_DIR`は、記録先だけを上書きする互換の手段として残す。指定があれば、すべての依頼をそこに記録する。

### 対象の決め方

サーバーは、次の順で対象を決め、決まらなければ依頼を拒否する（fail-closed）。推測では決めない。

1. 起動時の`--repo`。この場合、AIが渡す`repo`は、同じ対象でなければ拒否する。
2. AIが呼び出しの引数`repo`で渡したパス。
3. `repo`がなく、クライアントが知らせたrootsがちょうど1つなら、そのroot。
4. それ以外（`repo`がなく、rootsが0個か2個以上）は拒否する。

決めたパスは、次をすべて満たさなければ拒否する。

- gitの作業ツリーの中である。最上位に正規化して対象とする。
- クライアントがrootsを知らせている場合は、そのどれかの中にある。
- 起動時に`--allow <dir>`が指定されている場合は、そのどれかの中にある。

### AIとUIとのやり取り

- `request_review`と`get_review_result`に、省略できる引数`repo`を足す。戻り値は変えない（ADR-0004）。
- UI専用のツールは、依頼IDに加えて対象を受け取る。UIは表示中の依頼票の対象を持ち回る。対象のパスはAIには返さない。
- 依頼票に対象（`repo`）を記録する。UIは依頼票の上部に対象を表示する。
- ブラウザで開く経路のURLは、対象と依頼IDを含む。

### 現在のクライアントの制約で変わること

- Claude Desktopの通常の会話: 1つのプロセスを会話で共有するので、rootsでは会話ごとの対象を決められない。AIは毎回`repo`を渡す必要がある。渡さなければ、上の規則により拒否される（rootsを1つだけ知らせている場合を除く）。
- Claude Code: リポジトリの`.mcp.json`で`--repo .`を付けて登録すれば（ADR-0011）、AIは`repo`を省略できる。rootsで作業フォルダが知らされる場合も同じ。
- rootsへの対応は未確認なので、確認できるまでは「AIが`repo`を渡す」を主な経路として作る。

## 理由

- 依頼の記録は、対象のコードと一緒にある方が、取り違えが起きない。リポジトリを移動・複製しても記録が付いていく。ADR-0007の推奨をそのまま既定にする。
- サーバーを対象ごとに登録し分ける形は、プロジェクトを増やすたびにクライアントの設定と再起動が要り、AIに見えるツールも増える（ADR-0004）。
- 対象を依頼の引数で受け取ると、プロセスを共有するクライアントでも、会話をまたいで取り違えない。ADR-0008が「1回の呼び出しは1つの会話の中で起きる」を頼りにしたのと同じ考え方である。
- AIが渡す値は、サーバーの印と違って、AIが作業中に使っているパスそのものなので、持ち回りの失敗は起きにくいと見込む（未検証）。
- 推測で対象を決めると、別のリポジトリに記録を書いたり、別のコードを依頼票に載せたりしうる。レビューの記録は、決まらなければ止める方が安全である（ADR-0007と同じ）。
- rootsは、クライアントが「人が許可したフォルダ」を伝える仕組みなので、使えるなら、AIの引数より信頼できる。AIの引数をrootsの中に限ることで、AIが任意の場所に`.inloop/`を作る経路を塞ぐ。

## 影響

- AIの文脈: `request_review`の引数にパス（数十文字）が増える。ツール定義の説明文も少し増える。戻り値は変わらない。
- 依頼IDだけでは依頼を特定できなくなる。UI専用のツール、`get_review_result`、記録の読み込み、ブラウザの経路のURLは、対象と組で扱う。
- 1つのプロセスが複数の記録ファイルを開く。ReviewStoreを対象ごとに持つ。
- いまの利用者の記録（inloopリポジトリの`.inloop/`）は、そのままinloopを対象とした記録として読める。
- 解析エンジンは、決まった対象のリポジトリを読む。解析エンジンを作るときの前提になる。
- `--state-dir`を使った登録は、互換のために残る。

## 却下した代替案

- 対象ごとにサーバーを登録し分ける: 背景のとおり。設定と再起動が増え、AIに見えるツールも増える。
- サーバーの作業ディレクトリを対象にする: Claude Desktopは`/`で起動する（ADR-0007）。プロセスを共有するので、会話ごとに変えられない。
- 記録を利用者のホームの1か所にまとめ、対象ごとに分けて保存する: 対象のリポジトリと記録が離れ、移動や複製で対応が切れる。
- 対象を決められないとき、直前の依頼の対象を使う: 別の会話の対象を使ってしまう（ADR-0008の問題）。

## 未決のこと

- 対象のパスを、依頼票とUIにどこまで見せるか（ホームを`~`にするか、など）。

利用者との確認（2026-10-11）で、次を決めた。

- gitの別の作業ツリー（`git worktree`）は、別の対象とし、記録を共有しない。ブランチごとにコードが違うため。
- 対象はgitの作業ツリーに限る。gitを使わないフォルダは拒否する。

## 検証

`npm test`で次を確かめる。

- 2つのリポジトリへの依頼が、それぞれの`.inloop/`に記録され、IDが独立すること
- `repo`がなく、rootsもない呼び出しを拒否し、何も記録しないこと
- rootsの外、`--allow`の外、gitの作業ツリーの外のパスを拒否すること
- 作業ツリーの中の下位のパスが、最上位に正規化されること
- UI専用のツールで、別の対象の依頼に回答できないこと

実際のクライアントで次を確かめる（未検証）。

- Claude DesktopとClaude Codeが、rootsに対応しているか。対応しているなら、何を知らせるか
- Claude Desktopの通常の会話で、AIが毎回`repo`を渡すか
