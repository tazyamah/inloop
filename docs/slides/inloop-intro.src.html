inloop

AIコーディングに、人間の納得感を取り戻すためのレビュー基盤

human-in-the-loop review for AI coding

v0.0.0（開発中）・MIT License・github.com/tazyamah/inloop

inloop（インループ）の紹介です。AIがコードを書く開発で、人間を「判断の輪（human-in-the-loop）」の中に入れ続けるための、レビュー基盤です。

今日の流れは、解決したい課題、仕組み（信頼境界・図・lint）、使い方、画面の例、現状と今後、の順です。全部で15分前後を想定しています。

先に一点だけ。バージョンはまだ0.0.0で、開発中のツールです。実際に確かめた範囲と、まだ確かめていない範囲を分けてお話しします。

課題：生成速度と理解速度のずれ

  • AIは、人がレビューしきれない量のコードを短時間で生成できる
  • 人が書いたコードを信頼できるのは、書く速度＝理解の速度で、書きながらレビューしているから
  • 理解が追いつかないまま、変更が積み上がる

問題の中心は、品質そのものではなく
生成速度と理解速度のずれ

AIの生成人の理解

（ずれのイメージ図。実測値ではありません）

AIコーディングの弱点としてよく挙がるのは、ハルシネーション、境界条件の見落とし、脆弱なコード、規約違反、テストの形骸化などです。ただ、その多くは人間が書いたコードでも起こります。

それでも「人が書いたほうが信頼できる」と感じるのは、人は書きながらレビューしているからです。書く速度が理解の速度と一致しています。AIは、レビューしきれない量を一気に出せるので、そこがずれます。

なので、inloopが直したいのは品質ではなく、このずれです。右の図は、あくまでイメージです。

二つの原則

① 納得感と保証を分ける

対象担い手方法
機能の正しさ人が納得仕様から書いた、人が読める受け入れテスト
安全性機械が保証不変条件、静的解析、ルールによる検査
注意の配分機械が示し、人が見る信頼境界ルールによる強調と必須レビュー

② レビューの構造を、AIの推測に依存させない

対象・順序・影響範囲・証拠は、コードから決定的に作る。AIが書くのは問いの文だけ。

一つ目の原則は、納得感と保証を分けることです。機能が意図どおり動くかは人が納得する。安全性、つまり意図しないことをしない、は人の注意力に頼らず機械が保証する。そして、危険な場所はどこかを機械が示して、人はそこに集中します。

二つ目は、依頼票の構造をAIの推測に任せないことです。どのコードを、どの順に、何を証拠に見せるかは、解析エンジンがコードから決めます。AIが書くのは、「この観点で見てほしい」という問いの文です。

なお、設計方針の表です。プロパティテストやファジングなど、方針としてはあるが未実装のものもあります。実装済みの範囲は「現状」のスライドで改めて示します。

inloop（push型）

push型の穴：AIが依頼しなかった所は誰も見ない。これを二層で塞ぐ。

必須ルールで自動

信頼境界に触れた変更は、解析エンジンが自動で依頼を作る。AIは取り消せない。

任意AIが追加

設計判断や曖昧な仕様など、AIが自分で見てほしい点を依頼に足す。

全体を眺めて見る対象を探すレビューは、探すこと自体が負担です。inloopは逆に、AIが機能ごとに「この観点で見てほしい」と依頼を出します。人が答えると、その結果で後続のタスクが動きます。

ただしpush型には、AIが依頼しなかった部分は誰も見ない、という穴があります。そこで二層にします。信頼境界に触れた変更は、ルールに基づいて解析エンジンが自動で必須の依頼を作り、AIは取り消せません。それ以外の設計判断などは、AIが任意の依頼として足します。

レビューUI

依頼票の項目だけを読んで描く。コードから関係を推し量らない
  • 同じcommit・同じ解析器・同じルールからは、同じ依頼票になる
  • 行き先を決められなかった参照は、推測でつながず「未解決」と表示する
  • AIが書けるのは、観点の文とシンボルIDの指定だけ。図の箱・線・テーブルには関与できない

依頼票は、解析エンジンがコードから作ります。TypeScriptの型解決で宣言と参照を求め、git diffで変わった行を求め、SQL文字列から読む・書くテーブルを取り出し、inloop.jsonのルールを当てます。

できた依頼票はJSONで記録に残り、画面はその項目だけを読んで描きます。エンジンが確かめていない線は引きません。同じ入力からは同じ出力になることを、サンプルを作るスクリプトを2回動かして確かめています。

解析で行き先を決められない参照は、推測でつながずに未解決として出します。ここが「AIの言葉がもっともらしいだけ」を防ぐ要です。

仕組み③：信頼境界に触れたら、必ず依頼される

// inloop.json（リポジトリ直下・commitする）
{
  "format": 1,
  "boundaries": [{
    "id": "db",
    "question": "DBに書く値は、検証した
      入力だけから作っているか",
    "match": [
      { "import": "node:sqlite" },
      { "symbols": ["server/db.ts#Db"] }
    ]
  }]
}

当て方は import / global / files / symbols の4種類。

  • 当たった変更の単位ごとに、エンジンが必須の依頼を作る。questionが人への問いになる
  • 会話の言葉では承認できない。必須の依頼は画面で人が答える
  • AIがinloop.jsonのルールを消しても、基点側のルールも効く。inloop.jsonの変更自体も必須の依頼
  • レイヤーの向き（mayUse）に反した使い方も必須の依頼
  • inloop checkで、必須の依頼がすべて承認済みかを確かめる

信頼境界ルールは、リポジトリ直下のinloop.jsonに書きます。左の例は、sqliteをimportしている、またはDBのシンボルを変えた、という変更に「DBに書く値は検証した入力だけから作っているか」という問いを付ける、というルールです。

当たった変更には、エンジンが必須の依頼を作ります。AIが依頼を取り消す経路を塞ぐために、必須の依頼は会話の「承認」という言葉では記録できず、画面で人が答えます。AIがルールを書き換えて弱めても、基点側のルールとの和を使うので、その範囲では効いたままです。inloop.jsonを変えること自体も必須の依頼になります。

最後にinloop checkで、必須の依頼がすべて承認済みかを確認できます。これがマージの条件です。

注意：実際のクライアントで、AIが必須の依頼を人に伝えるか、作業の終わりにinloop checkを動かすかは、まだ確かめていません。

依頼票の図：依存の図

実際のエンジンが作った依頼票を、実際のレビューUIで撮ったもの（docs/diagrams.md）

  • 依頼に並べたシンボルどうしの「使う関係」。呼び出し元の列、変更・未解決の印つき
  • 並べる順は理解順（定義が使用より先）
  • テーブルの一覧、レイヤーと境界の札、再依頼の畳みも同じ依頼票から描く

作らないER図とデータフロー図は生成しません。値の流れは今の解析では追えず、作れないものを作れるふりをしないため、名前も「データの流れ」ではなく「依存の図」にしています。

依頼票に出る図の一つ目が依存の図です。依頼に並べたシンボルどうしの使う関係を、SVGで描きます。変更した箱、未解決の印、呼び出し元の列が付きます。

ここで正直にお伝えしておくと、ER図とデータフロー図は作っていません。値がどの引数からどこへ渡るかは、今の解析エンジン、つまり呼び出し関係までの解析では追えません。そのため図の名前も「データの流れ」ではなく「依存の図」にしています。作る場合は、新しい解析が要るので、改めて設計判断を立てます。

依頼票の図：ユースケース図 入口ごとのデータとテスト

docs/diagrams.md のサンプル（tasks-demo）

  • HTTPの入口（ルート）ごとに、読む・書くテーブルと列、その入口へ要求を送るテストを結ぶ
  • inloop.jsonにusecasesを書いたアプリだけ。inloop usecasesで一覧も出せる
  • データフロー図ではない（入口・テーブル・テストを結ぶだけ）

未実クライアントでの使用、既存アプリでの偽陽性、サーバー向け以外の雛形への適用は未確認

二つ目の図がユースケース図です。HTTPの入口ごとに、どのテーブルのどの列を読み書きするか、その入口に要求を送るテストはどれか、を結びます。「この機能はどのデータに触れて、どのテストで守られているか」を一目で見るためのものです。

inloop.jsonにusecasesを書いたアプリだけで出ます。サーバー向けの雛形に入れてあります。先ほど言ったとおり、値の流れを追うデータフロー図ではありません。自動テストとChromiumでの表示までは確認していますが、実際のClaude Codeでの使用や、既存アプリでの偽陽性は未確認です。

仕組み④：危険な書き方を、書けなくする inloop lint

  • IPAの注意喚起（2026-10-09）から導いた14の規則を、構文木で検査する
  • sec-bind／sec-cors／sec-secret／sec-crypto／sec-tls／sec-cleartext／sec-log／sec-sql-literal／sec-shell／sec-eval／sec-html／sec-stack／sec-unchecked／secure-gate
  • コメントで無効にする書き方は作らない。例外はinloop.jsonに理由つきで書き、その変更は必須の依頼になる
  • 検査器は、アプリではなくinloop本体にある（AIがコピーを書き換えられない）

違反すると失敗する場所

  • inloop check（マージの条件）
  • 雛形のnpm testとnpm run build
  • inloop generate scaffoldの生成後

未自動テストまで確認。実際のClaude Codeでの自力修正と、既存アプリでの偽陽性は未確認

もう一つ、人が見る前に「そもそも書かせない」ための仕組みがinloop lintです。IPAの注意喚起から導いた規則を、構文で決まる範囲に限って検査します。待ち受けをloopbackに限る、CORSを*にしない、秘密情報をコードに書かない、証明書検証を無効にしない、生のSQL文字列を組み立てない、などです。

構文で決まるものだけを対象にしたのは、同じ入力から同じ結果になり、AIの判断が挟まらないようにするためです。無効化コメントは用意していません。例外はinloop.jsonに理由つきで書き、その変更が必須の依頼になるので、AIが勝手に例外を足しても、人が理由を確かめるまではinloop checkが通りません。

こちらも自動テストまでの確認で、実際の会話での使い勝手や偽陽性は、これから確かめます。

使い方：最短の手順

# 入れる（Node.js 22.13以上、git、Claude Code）
git clone https://github.com/tazyamah/inloop.git
cd inloop && npm ci && npm run build
export PATH="$PWD/bin:$PATH"

# アプリを作る（React＋Hono＋SQLite）
inloop new myapp && cd myapp
npm install && npm run dev

# 表・API・テスト・画面を生成
inloop generate scaffold task title:text \
  done:bool due:date:optional

# 必須の依頼がすべて承認済みか
inloop check
  1. inloop newが、アプリに.mcp.jsonを書く
  2. そのフォルダをClaude Codeで開く（初回は、inloopのMCPサーバーの使用を許可）
  3. 「○○を管理する機能を作って」と頼む
  4. 信頼境界に触れた変更に、レビュー依頼が出る
  5. 表示されるURLをブラウザで開き、承認か保留を押す

動作を確かめているのはmacOSです。Linux・Windowsは未確認。

使い方です。inloop本体をcloneしてビルドし、binをPATHに通します。Node.jsは22.13以上、gitとClaude Codeが要ります。

inloop newでアプリを作ると、標準の構成はReactとHonoとSQLiteです。inloop newはアプリに.mcp.jsonを書くので、そのフォルダをClaude Codeで開くと、inloopのMCPサーバーが使えます。「○○を管理する機能を作って」と頼むと、AIが変更を作り、信頼境界に触れた部分にレビュー依頼が出ます。

表示されるURLをブラウザで開いて内容を確かめ、承認か保留を押します。最後にinloop checkで、必須の依頼がすべて承認済みか確かめます。なお、動作確認はmacOSだけです。

人の回答で、後続のタスクが動く

[inloop] レビュー回答。fixは修正後に
request_reviewのfollowsで再依頼、askは会話で答える:
R12 ok
R13 fix src/auth.ts#login#L42 "トークン期限切れは401で返す"
R13 ask src/auth.ts#login#L50-L53 "リトライは冪等?"
R15 hold

回答は1行1件。まとめて1通でAIへ返る（docs/review-protocol.md）

値意味
ok承認
fix修正依頼（コメント必須）
ask質問（コメント必須）
hold保留
  • 修正後は、前回からの差分だけを再依頼（承認時のシンボル本文のハッシュと比べる）
  • マージの条件は、再依頼済みを除くすべての依頼が承認済みであること

人の回答は、承認のok、修正依頼のfix、質問のask、保留のholdの4種類です。fixとaskはシンボルや行を指してコメントを付けられます。画面の「まとめて送信」で、1行1件の短い形式の1通にまとまってAIに返ります。

fixの場合、AIが直してから再依頼します。このとき、承認時に記録したシンボル本文のハッシュと比べて、変わった部分だけを見せます。承認済みの部分は畳みます。マージの条件は、再依頼済みを除くすべての依頼が承認済みであることです。

次の一手

  1. scaffoldを実際のClaude Codeで使い、足りないもの（関連、並べ替え、検索、列の型など）を洗い出す
  2. データの書き出し・読み込みのiPhone確認、拡張からの共有の実機確認
  3. lint・ユースケース図の偽陽性を、既存アプリで確かめる
  4. 再依頼の畳み方（保留のあとも畳むか、行単位の差分が要るか）

今後の方針は、利用者の方針として、まずClaude Code（デスクトップ）でWebアプリとデスクトップアプリを楽に作れるようにすることです。他のクライアント、DB、OSは、それが済んでからにします。ただし設計は、後から足せるようにしておきます。

次の一手は四つです。scaffoldを実際の会話で使って足りないものを洗い出す。データの書き出し・読み込みや共有の実機確認。lintとユースケース図の偽陽性の確認。それから、再依頼の畳み方の判断です。
